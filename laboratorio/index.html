Introdução

O desafio de auditoria

Do código à evidência: como investigar, comparar e comunicar resultados de segurança.

Do código à evidência

Você participará de uma auditoria de segurança de uma API REST utilizada por empresas fictícias para registrar, consultar, alterar e aprovar pedidos. O sistema já existe, possui funcionalidades implementadas e uma arquitetura organizada. Seu desafio não é desenvolver uma aplicação do zero, mas investigar como o código aplica as regras de segurança, identificar problemas ou hipóteses, comparar métodos de análise e demonstrar a efetividade de correções selecionadas.

A investigação acontecerá progressivamente. Você começará pela leitura humana do código, passará por ferramentas de análise estática, examinará fluxos de dados e respostas assistidas por IA e terminará com uma auditoria integrada. Ao longo do caminho, será necessário justificar suas conclusões com evidências. Um alerta de ferramenta pode indicar uma pista, mas não substitui a compreensão do contexto nem comprova, sozinho, que houve uma exploração.

Atenção

O projeto é um caso de treinamento deliberadamente vulnerável, com dados fictícios. Utilize apenas ambiente local e isolado. Não disponibilize a API publicamente, não introduza dados pessoais reais e não publique segredos nos repositórios.

O que você deverá ser capaz de demonstrar

Ao final do percurso, espera-se que você consiga explicar uma regra de segurança, localizar os componentes de código responsáveis por ela, indicar se existe evidência de descumprimento, comparar resultados entre técnicas manuais e automatizadas e comunicar uma correção com seus testes e limitações. A qualidade do trabalho é medida pela coerência do raciocínio e pela rastreabilidade da análise, não pela quantidade de alertas encontrados.

Contexto técnico

Sistema que será analisado

Uma API REST multi-tenant para gerenciamento de pedidos, construída com Node.js, TypeScript, Express, Prisma e PostgreSQL.

Contexto de negócio

Duas organizações fictícias utilizam a mesma API para gerenciar solicitações de compra. Cada pessoa tem identidade própria, pertence a uma organização e recebe um papel de acesso. Alguns usuários criam pedidos; outros podem consultá-los ou aprová-los. Há também relatórios e exportações de dados.

Esse cenário é comum em sistemas corporativos: compartilhar uma infraestrutura não significa compartilhar todos os dados. É necessário controlar não apenas quem fez login, mas também o que essa pessoa pode executar, em qual organização e sobre qual recurso específico.

Arquitetura em camadas

O projeto utiliza Node.js, TypeScript, Express, Prisma, PostgreSQL, JWT e Zod. O código está organizado por funcionalidade em auth, users, orders e reports, e cada módulo separa responsabilidades.

REQUISIÇÃO HTTP
      │
      ▼
Routes + middlewares (autenticação, validação, autorização geral)
      │
      ▼
Controller (adapta entrada e resposta HTTP)
      │
      ▼
Service (decide as regras de negócio e políticas contextuais)
      │
      ▼
Repository (consulta e altera dados persistidos)
      │
      ▼
Prisma ORM  →  PostgreSQL

Routes definem verbos e caminhos e conectam middlewares aos controllers. Controllers recebem dados da requisição e produzem respostas HTTP; não devem concentrar regras de negócio nem consultar o Prisma diretamente. Services coordenam os comportamentos de negócio, como validação de estado do pedido, autorização contextual e limites entre organizações. Repositories encapsulam consultas, filtros e alterações na base de dados. Schemas Zod verificam formatos e campos permitidos em entradas, mas não substituem autorização. Middlewares autenticam e aplicam controles transversais.

O sistema utiliza JWT real. Após autenticar por e-mail e senha, o cliente recebe um token e o envia nas requisições privadas no header Authorization: Bearer <token>. A existência de um token válido comprova que houve autenticação nos termos aceitos pela API, mas não significa permissão para consultar qualquer registro.

Como transformar um requisito em uma pergunta de auditoria

Veja uma regra fictícia independente deste laboratório: "Somente o autor de uma anotação privada pode editá-la". Isso exige pelo menos quatro perguntas: o endpoint exige autenticação? O serviço identifica o autor da anotação? A operação consulta ou altera apenas a anotação permitida? O sistema rejeita uma tentativa de editar a anotação de terceiro? Essas perguntas guiam a leitura e indicam testes para obter evidência. Um teste que apenas confirma a edição válida não verifica, por si só, a proibição de edição por terceiros.

Dica metodológica

Matriz de análise: para cada requisito, registre o método HTTP, o papel, a organização, o recurso, o estado relevante, o fluxo de código e a evidência encontrada. Se algo não puder ser verificado, marque "não avaliado" ou "inconclusivo", não "seguro".

git clone <URL_REAL_DO_REPOSITORIO_DA_EQUIPE>

3. Execute o diagnóstico.

npm run doctor

Esse comando verifica requisitos básicos do ambiente e informa possíveis ausências. Ele não instala automaticamente Docker ou Node.js, pois isso depende das permissões e do sistema operacional do computador.

4. Prepare o ambiente.

npm run setup

O script foi desenhado para criar o .env local quando não existir, instalar dependências, iniciar o PostgreSQL pelo Docker Compose, gerar o Prisma Client, aplicar migrations e carregar dados fictícios. 5. Inicie a aplicação.

npm run dev

Em outro terminal, ou no navegador, consulte http://127.0.0.1:3000/health. A resposta esperada é um JSON com estado ok. Isso apenas confirma que a API responde, não que todos os requisitos de segurança estejam atendidos.

6. Faça uma verificação funcional básica.

npm run test:smoke

Esse comando executa testes básicos de funcionamento e não substitui os testes de segurança. A execução completa do projeto e dos scripts deve ser validada no ambiente local antes de sua distribuição oficial, pois o pacote inicial ainda passou por validação parcial.

7. Nas próximas utilizações: o projeto disponibiliza npm run lab para verificar ou iniciar o banco e executar a API, e npm run db:stop para interromper os containers sem remover os volumes.

Metodologia

Como investigar e registrar evidências

A diferença entre observar, suspeitar e confirmar. Oito movimentos para uma revisão rastreável.

A diferença entre observar, suspeitar e confirmar

Durante uma revisão de segurança, você encontrará linhas preocupantes, configurações incompletas, alertas de ferramentas e situações que parecem contradizer os requisitos. Nem tudo tem o mesmo peso como evidência.

Hipótese

Existe uma possibilidade de falha que ainda precisa de confirmação. Exemplo ilustrativo: "A rota de download recebe um identificador, e ainda não encontramos uma verificação de proprietário". Essa afirmação indica um caminho de investigação, mas não garante que o acesso indevido seja possível.

Achado confirmado

A equipe consegue demonstrar, por leitura completa do fluxo e/ou execução controlada, um comportamento que viola uma regra de segurança, indicando a condição, o local, o impacto e o resultado observado. Um teste negativo reproduzível torna o achado mais robusto.

Alerta que exige contexto

Uma ferramenta identificou uma construção potencialmente perigosa, mas faltam informações sobre dados de entrada, alcance, permissões e proteções. A conclusão deve permanecer aberta até a triagem.

Falso positivo

O alerta foi investigado e as evidências mostram que a condição acusada não corresponde a uma vulnerabilidade naquele contexto. A classificação precisa ser justificada. Não chame de falso positivo apenas porque a correção é inconveniente ou porque o sistema aparentemente funciona.

Inconclusivo

Os dados disponíveis não permitem decidir com segurança. É um resultado válido quando acompanhado da limitação e da próxima verificação necessária.

Método de inspeção em oito movimentos

  1. Escolha um requisito. Leia a regra esperada, identifique quem pode executar a ação e em quais condições.
  2. Localize o endpoint. Encontre a rota correspondente e os middlewares aplicados.
  3. Percorra as camadas. Siga controller, service e repository; observe os valores transportados entre elas.
  4. Identifique a fronteira de confiança. Pergunte quais valores são controlados pelo cliente e quais são obtidos de fonte confiável após autenticação.
  5. Compare comportamento e regra. Descubra onde a autorização, a validação e as condições de estado deveriam ocorrer.
  6. Formule um cenário negativo. Pense em um usuário, recurso, organização ou estado para o qual a operação deveria ser recusada.
  7. Colete evidências. Registre arquivo/função, commit, configuração, passos executados e resposta observada; se não executou, explicite que se trata de inspeção estática.
  8. Classifique e recomende. Defina o grau de confiança, o efeito potencial, a correção e a forma de reavaliar o risco.

O objetivo não é procurar apenas padrões com palavras como unsafe ou password. Em um back-end organizado, uma vulnerabilidade pode resultar da ausência de uma verificação em uma camada, apesar de todas as funções compilarem e os retornos serem válidos.

Exemplo didático: evidência insuficiente versus evidência rastreável

Exemplo genérico, não pertencente ao código do projeto. Imagine uma API fictícia de notas privadas.

Insuficiente

"Vulnerabilidade crítica. A função busca por ID e não usa o usuário."

Esse registro, isoladamente, é insuficiente. Pode existir uma verificação antes ou depois da consulta. O código pode não ser alcançável por nenhum endpoint. Não há ator, requisito nem prova do comportamento observado.

Rastreável

"Hipótese H-01. Na funcionalidade fictícia GET /notes/:id, a rota exige login, mas a verificação de titularidade ainda não foi localizada no fluxo percorrido até o repository. A regra exige que cada usuário visualize somente notas próprias. Próxima verificação: autenticar como usuário B e tentar consultar uma nota pertencente ao usuário A, preservando o status HTTP e sem incluir tokens no registro. Situação atual: hipótese, não confirmada."

Etapa 1

Reconhecimento do projeto

Pergunta orientadora: o que estamos protegendo e onde estão os controles?

Antes de procurar falhas, compreenda o sistema. Saber que uma API tem JWT, validação Zod e banco PostgreSQL não é suficiente para afirmar que ela está segura. A primeira tarefa é entender os atores, os recursos, os caminhos de entrada e os componentes responsáveis por controlar cada ação.

Seu percurso

  1. Acesse o repositório da equipe e leia README.md e docs/REQUISITOS_NEGOCIO.md.
  2. Identifique os módulos em src/modules/ e desenhe a passagem de uma requisição desde a route até o repository.
  3. Liste as rotas e diga quais exigem autenticação e quais podem depender de autorização por papel, organização, proprietário ou estado.
  4. Examine prisma/schema.prisma para entender relações entre usuários, organizações e pedidos. Não é necessário dominar todos os recursos do Prisma para perceber relações de titularidade e escopo.
  5. Se a API estiver executável, realize login com uma conta fictícia autorizada e consulte uma rota funcional. Diferencie teste de conectividade de teste de segurança.
  6. Registre hipóteses, sem chamá-las prematuramente de vulnerabilidades. Para cada hipótese, indique qual requisito e fluxo precisam ser investigados.

O registro esperado

Em entregas/01_inventario.md, inclua o objetivo do sistema, lista resumida de atores e recursos, uma tabela das rotas, desenho das camadas, requisitos prioritários e hipóteses para inspeção. Identifique o commit inicial que será preservado como linha de base.

Exemplo de registro genérico

"A rota fictícia POST /documents/:id/share exige autenticação. Ainda precisamos verificar se a operação valida a propriedade do documento e a permissão para compartilhá-lo. Requisito a conferir: acesso apenas ao recurso autorizado. Evidência atual: leitura da route; situação: hipótese."

Critérios de conclusão

Você consegue explicar a finalidade de cada módulo, localizar uma route, seguir seu controller/service/repository, identificar as dimensões de autorização do sistema e apontar hipóteses com seus próximos passos. Não é necessário encontrar um número mínimo de falhas nesta etapa.

Etapa 2

Revisão manual independente

Pergunta orientadora: o código realmente cumpre as regras de negócio?

Uma revisão manual de segurança não se limita a procurar funções suspeitas. Ela compara a implementação com requisitos explícitos de segurança. Nessa etapa, o resultado humano deve ser registrado antes do contato com resultados de Semgrep, CodeQL e ferramentas de IA, de modo que possamos comparar abordagens depois sem contaminar a linha de base.

Percurso de revisão

Passo 1: selecione um requisito. Por exemplo, RN-07: aprovar exige papel apropriado, organização correspondente e pedido pendente. O estudante deve verificar cada condição no fluxo de código, em vez de presumir que uma delas implica as outras.

Passo 2: percorra o caminho completo. Abra a route, localize os middlewares, siga o controller, observe as decisões no service e inspecione os filtros no repository. Anote onde cada condição é verificada e como o sistema responde quando ela não é satisfeita.

Passo 3: formule cenários negativos. Pense na diferença entre acesso permitido e acesso indevido. Uma operação pode funcionar para um usuário legítimo e falhar em proteger um usuário ou organização diferente.

Passo 4: registre hipóteses e confirmações. Associe o registro ao RN, commit, trecho de código e eventual teste. Não inclua segredos, tokens completos ou dados que não sejam os fictícios do case.

Passo 5: preserve a revisão independente. Faça commit do documento com sua análise e guarde o hash. As ferramentas automatizadas serão utilizadas depois dessa linha de base.

Revisão cruzada entre equipes

Quando a revisão inicial estiver registrada, outra equipe poderá examinar suas conclusões nos termos do acesso concedido no GitHub. A tarefa é questionar a qualidade das evidências, não apenas concordar ou discordar.

A equipe revisora deve verificar: o requisito está corretamente interpretado? O trecho citado pertence ao fluxo executável? O comportamento alegado foi demonstrado ou é somente hipótese? Há controle em outra camada? A classificação é justificada? Um teste negativo verificaria o problema? Uma recomendação poderia introduzir regressão?

Comentário útil

"A hipótese é plausível, mas seria necessário inspecionar a verificação de organização no Service antes de classificá-la como confirmada. O teste proposto também deveria comparar usuários de organizações diferentes."

Comentário insuficiente

"Parece vulnerável", sem indicação de requisito, contexto ou evidência.

O registro esperado

Em entregas/02_revisao_manual.md, reúna escopo, requisitos investigados, achados confirmados e hipóteses, localização de código, evidências, resultados de testes negativos quando disponíveis, recomendações e notas de revisão cruzada. Limitações importantes dessas regras

As regras 4 e 5 usam o nome literal prisma. Se a aplicação usar outro nome de variável ou um repository que encapsule o cliente, essas regras não produzirão alertas.

A regra de SQL usa uma expressão regular textual. Uma correspondência com $queryRawUnsafe não demonstra por si só a existência de SQL Injection: é necessário investigar como a consulta é construída e quais dados chegam a ela.

Essas limitações fazem parte do aprendizado sobre cobertura e falsos negativos em análise estática.

Problemas frequentes

  • Geral Docker: comando não reconhecido

    Se o terminal exibir docker: command not found ou 'docker' não é reconhecido, o Docker não está instalado ou não foi adicionado ao PATH. Acesse Preparar o ambiente e siga as instruções de instalação do Docker Desktop.

    Depois de instalar, feche e reabra o terminal para recarregar o PATH.

  • Geral Docker Engine não iniciado

    Erro: Cannot connect to the Docker daemon at unix:///var/run/docker.sock ou similar.

    Abra o Docker Desktop e aguarde o ícone ficar verde na bandeja do sistema. Só então execute o comando novamente.

  • Git Bash Quebras de linha CRLF no YAML

    Se o arquivo YAML foi editado no Windows com quebras de linha CRLF, o Semgrep pode falhar ao interpretar o arquivo. Converta para LF antes de executar:

    sed -i 's/\r//' rules/minha-regra.yml

    No VS Code, clique em "CRLF" no canto inferior direito e selecione "LF" para salvar com as quebras corretas.

  • Git Bash Conversão automática de caminhos

    No Git Bash no Windows, o shell converte /src para C:/Program Files/Git/src automaticamente. Para evitar isso, sempre use MSYS_NO_PATHCONV=1 antes do comando Docker e $(pwd -W) para o caminho do projeto:

  -v "$(pwd -W):/src" \
  -w /src \

  --config rules/classroom.yml src

    • O nome do arquivo está correto, incluindo extensão .yml.

    Erro: Invalid rule schema ou YAML parse error. Problemas comuns:

    • Indentação com tabs em vez de espaços — YAML usa apenas espaços.

Glossário CWE

As regras do Semgrep referem-se a categorias de fraquezas do catálogo CWE (Common Weakness Enumeration). Os termos abaixo aparecem com frequência nos alertas e no relatório.

  • CWE-78 Injeção de Comando do SO
    O que é

    A aplicação constrói um comando de sistema operacional usando dados controlados pelo usuário sem validação ou sanitização adequada. Um atacante pode inserir argumentos extras ou separadores de comando para executar instruções arbitrárias no servidor.

    Exemplo de risco

    exec("ping " + req.query.host) — se host for ; rm -rf /, o comando de limpeza será executado no servidor.

    O que investigar

    Rastreie a origem do argumento passado a funções como exec, spawn, execSync. Verifique se existe validação antes da chamada.

    MITRE CWE-78
  • CWE-89 Injeção de SQL
    O que é

    Dados do usuário são inseridos diretamente em consultas SQL sem parametrização, permitindo manipulação da lógica da consulta.

    Exemplo de risco

    "SELECT * FROM users WHERE id = " + req.params.id — com id = 1 OR 1=1, retorna todos os registros.

    O que investigar

    Verifique se as consultas usam prepared statements ou ORM com parâmetros vinculados. Concatenação de strings em queries é um sinal de alerta.

    MITRE CWE-89
  • CWE-639 Referência Direta a Objeto (IDOR)
    O que é

    O sistema usa um identificador controlado pelo usuário (como um ID na URL) para acessar diretamente um recurso sem verificar se o usuário autenticado tem permissão para aquele ID específico.

    Exemplo de risco

    GET /api/pedidos/1234 — se o backend busca o pedido pelo ID sem verificar se pertence ao usuário da sessão, qualquer usuário pode acessar qualquer pedido.

    O que investigar

    Após buscar o recurso pelo ID da URL, o código verifica se recurso.userId === req.user.id (ou equivalente)?

    MITRE CWE-639
  • CWE-862 Autorização Ausente
    O que é

    Um recurso ou operação não verifica se o usuário autenticado tem permissão para realizá-la. A autenticação confirma quem é o usuário; a autorização confirma o que ele pode fazer.

    Exemplo de risco

    Rota DELETE /api/usuarios/:id sem verificar se o chamador tem papel de administrador.

    O que investigar

    Existe algum middleware ou guard de autorização aplicado a esta rota? Apenas autenticação (JWT válido) não é suficiente para operações privilegiadas.

    MITRE CWE-862
  • CWE-863 Autorização Incorreta
    O que é

    O sistema verifica autorização, mas com lógica ou dados incorretos — por exemplo, usando um campo que o usuário pode manipular para elevar seus privilégios.

    Exemplo de risco

    Verificar o papel do usuário a partir do próprio payload do JWT sem validar a assinatura, permitindo que qualquer pessoa crie um token com "role": "admin".

    O que investigar

    O dado usado para decidir o nível de acesso vem de uma fonte confiável (banco de dados, sessão do servidor) ou de algo que o usuário pode modificar?

    MITRE CWE-863
  • CWE-915 Atribuição em Massa
    O que é

    O sistema copia automaticamente campos do corpo da requisição para um objeto sem filtrar quais campos são permitidos. Um atacante pode enviar campos extras (como role ou isAdmin) que não deveriam ser modificáveis.

    Exemplo de risco

    Object.assign(usuario, req.body) — se req.body incluir "isAdmin": true, o campo será atualizado sem validação.

    O que investigar

    O código usa allowlist (lista de campos permitidos) ao atualizar objetos com dados da requisição?

    MITRE CWE-915
  • CWE-841 Fluxo de Autenticação Desrespeitado
    O que é

    A aplicação define um fluxo esperado (ex.: verificar email antes de ativar conta), mas permite que etapas obrigatórias sejam puladas acessando diretamente endpoints posteriores.

    Exemplo de risco

    Um fluxo de redefinição de senha com etapas 1 (email), 2 (código) e 3 (nova senha) que permite acessar a etapa 3 diretamente sem passar pela 2.

    O que investigar

    O backend valida que o estado anterior foi concluído antes de processar a etapa seguinte? Ou confia apenas no que o cliente envia?

    MITRE CWE-841
  • CWE-20 Validação de Entrada Insuficiente
    O que é

    O sistema não verifica suficientemente se os dados recebidos têm o formato, tipo, tamanho ou conteúdo esperado. É a categoria raiz de muitas outras fraquezas.

    Exemplo de risco

    Um campo numérico que aceita strings arbitrárias, ou um campo de email que aceita qualquer valor sem verificar o formato.

    O que investigar

    Existe validação de schema (ex.: Zod, Joi, class-validator) aplicada antes de usar os dados? A validação cobre todos os campos relevantes?

    MITRE CWE-20
  • CWE-200 Exposição de Informação Sensível
    O que é

    O sistema revela dados que não deveriam ser acessíveis — stack traces em respostas de erro, campos de senha em respostas JSON, logs com dados pessoais ou credenciais.

    Exemplo de risco

    Resposta de erro que inclui o stack trace completo com caminhos internos do servidor e versões de bibliotecas.

    O que investigar

    O que é retornado nas respostas de erro? Alguma resposta inclui campos como password, hash ou token?

    MITRE CWE-200
  • CWE-287 Autenticação Imprópria
    O que é

    O mecanismo de autenticação tem falhas que permitem que um usuário prove identidade de forma incorreta ou inadequada.

    Exemplo de risco

    Verificar apenas se o token JWT existe sem validar sua assinatura, ou aceitar o algoritmo none que não exige assinatura.

    O que investigar

    O código usa jwt.verify() (que valida a assinatura) ou apenas jwt.decode() (que não valida)? O algoritmo é fixo no código ou confiado ao token?

    MITRE CWE-287
  • CWE-798 Credencial Fixa no Código
    O que é

    Senhas, tokens, chaves de API ou segredos são embutidos diretamente no código-fonte em vez de serem lidos de variáveis de ambiente ou sistemas de gestão de segredos.

    Exemplo de risco

    const JWT_SECRET = "minha-senha-secreta-123" no código — qualquer pessoa com acesso ao repositório obtém o segredo.

    O que investigar

    Existe alguma string que parece uma senha, token ou chave definida como constante no código? Os segredos são lidos de process.env?

    MITRE CWE-798

Etapa 4

Fluxo de dados, CodeQL e IA

Pergunta orientadora: de onde veio o dado e a que operação ele chegou?

Uma vulnerabilidade pode depender de como valores atravessam funções e camadas. Em análise de fluxo, identificamos uma source (ponto onde dados de interesse entram), acompanhamos a propagação e investigamos um sink (operação sensível). O percurso pode passar por route, controller, service e repository, e por isso é importante olhar além de um único arquivo.

Percurso com CodeQL

  1. Escolha um alerta ou exemplo de fluxo disponibilizado para esta etapa.
  2. Identifique a source, o sink, as funções intermediárias e possíveis validações ou sanitizações.
  3. Registre o caminho de dados em um diagrama, indicando os arquivos e a natureza de cada transformação.
  4. Avalie se a trajetória demonstrada é executável nas condições do projeto ou apenas uma relação de código de interesse.
  5. Declare como o resultado foi obtido: consulta executada pela equipe, demonstração pública controlada ou relatório disponibilizado.

Atenção à infraestrutura

A integração de CodeQL/Code Scanning em repositórios privados pode exigir licenciamento não disponível na organização gratuita. Se o ambiente privado não permitir a execução, a atividade pode utilizar um repositório público demonstrativo e resultados disponibilizados pelo Moodle. A ausência de licença não invalida o objetivo de interpretar o método. Não invente saídas de CodeQL para preencher o relatório.

Exemplo conceitual (não é gabarito do projeto):

Parâmetro da URL (source)
       ↓
Controller recebe a requisição
       ↓
Service transforma ou encaminha o valor
       ↓
Repository constrói a operação
       ↓
Consulta ou chamada sensível (sink)

Um dado atravessar várias funções não significa automaticamente que a aplicação é vulnerável. A conclusão depende da semântica da operação, do controle dos valores, das validações e das barreiras existentes.

Percurso de IA

A IA é introduzida depois da revisão manual independente e da etapa de SAST. Uma ferramenta generativa pode sugerir hipóteses, cenários negativos e melhorias, mas também pode omitir controles, atribuir comportamentos inexistentes ou afirmar exploração sem prova.

  1. Escolha trechos fictícios permitidos para análise. Não compartilhe .env, JWT, senhas, dados reais ou informações institucionais sensíveis.
  2. Registre nome da ferramenta e modelo, data do uso, contexto e requisitos fornecidos.
  3. Peça hipóteses com arquivo/função, requisito relacionado, condição de alcance e teste que poderia confirmar ou refutar cada hipótese.
  4. Preserve a resposta original e avalie cada afirmação lendo o código ou usando um teste real quando viável.
  5. Classifique o resultado como confirmado, não confirmado ou inconclusivo, explicando a evidência.
  6. Compare as hipóteses com a revisão manual e as ferramentas de análise estática.

Comparação de técnicas e CI/CD

Pergunta orientadora: por que métodos diferentes produzem resultados diferentes?

Revisão manual, Semgrep, CodeQL e IA observam o código de formas diferentes. A revisão manual pode considerar regras de negócio, mas depende da experiência e do tempo do analista. Regras estáticas podem encontrar padrões em grande escala, mas não compreendem automaticamente todo o contexto. Ferramentas de fluxo podem seguir propagação entre componentes dentro de seus modelos.   5. Identifique quais confirmações vieram de execução real e quais permanecem fundamentadas somente em inspeção estática.

Etapa 6

Correções, testes e auditoria integrada

Pergunta orientadora: como demonstrar que uma correção funcionou?

Encontrar uma falha e alterar uma função são atividades diferentes de comprovar que o problema foi remediado. A validação precisa confrontar o comportamento anterior e posterior em cenários de sucesso e de negação de acesso. Também é necessário identificar riscos que permanecem fora da cobertura dos testes.

Percurso de correção e validação

  1. Priorize: selecione problemas com justificativa de risco e critérios que possam ser verificados.
  2. Preserve a linha de base: identifique o commit da versão inicial e a evidência anterior à correção.
  3. Crie uma branch ou Pull Request: implemente a alteração de forma localizada, respeitando as camadas e os requisitos de negócio.
  4. Execute testes positivos e negativos: um acesso legítimo deve continuar funcionando e o acesso indevido deve ser recusado. Verifique estados e organização quando aplicáveis.
  5. Reexecute análises relevantes: quando a ferramenta estiver disponível, repita a varredura e compare resultados no mesmo escopo e com regras declaradas.
  6. Registre antes e depois: indique commits, entradas, papéis, resposta esperada, resposta observada e diferenças.
  7. Avalie o risco residual: descreva quais cenários não foram cobertos, quais dependências ou integrações não foram verificadas e o que seria necessário em uma auditoria de produção.
  8. Consolide o relatório: apresente escopo, método, resultados, comparação, correções e conclusões sustentadas por evidências.

Detalhamento dos critérios

C1, revisão manual (30 pontos): até 10 pontos pelo uso adequado dos requisitos e do escopo; até 10 pontos por achados com evidência e possibilidade de reprodução; até 5 pontos pela elaboração/interpretação de testes negativos; até 5 pontos pela qualidade da revisão cruzada e do raciocínio técnico. Um texto afirmando que algo está vulnerável, sem mostrar o motivo, não satisfaz os critérios de evidência.

C2, SAST (25 pontos): até 8 pontos pelo registro de versão, regras, escopo e origem dos resultados; até 8 pontos pela interpretação e triagem dos alertas; até 5 pontos por uma regra Semgrep própria com teste positivo e negativo; até 4 pontos por investigação de CodeQL ou alternativa disponibilizada e documentada. Quando o ambiente institucional não permitir uma ferramenta, identifique honestamente a alternativa usada.

C3, comparação crítica (25 pontos): até 10 pontos por matriz que consolida o mesmo achado entre métodos sem duplicar contagens; até 8 pontos pela discussão de falsos positivos, ausências de detecção e hipóteses da IA validadas; até 7 pontos pela explicação da cobertura, alcançabilidade, limitações e complementaridade das abordagens.

C4, correções e validação (20 pontos): até 10 pontos por correções coerentes com os requisitos, implementadas de modo controlado; até 7 pontos por testes de regressão com evidências antes e depois; até 3 pontos por registro de risco residual e qualidade do relatório final.

O que distingue um trabalho fundamentado

Um trabalho consistente não precisa encontrar o maior número de falhas. Ele explica o que foi inspecionado, como foi testado, qual evidência sustenta cada conclusão e o que continua desconhecido. Uma análise parcialmente inconclusiva, mas transparente e tecnicamente coerente, é mais útil que uma lista de "vulnerabilidades críticas" sem justificativa.

As atividades podem ser feitas em equipe, mas todos os integrantes devem compreender as conclusões apresentadas e ser capazes de explicar as principais decisões do relatório.

FAQ

Dúvidas frequentes

Respostas para as perguntas mais comuns sobre o laboratório.

  • Preciso conhecer Node.js, TypeScript ou Docker previamente?

    Não é necessário dominar a stack para começar a inspeção. É importante, porém, aprender a localizar routes, controllers, services e repositories e compreender as regras de negócio. A execução local ajuda na reprodução de cenários; se houver dificuldades, utilize o guia de instalação, a colaboração da equipe e os materiais disponibilizados para contingência. A instalação, isoladamente, não é componente da nota.

  • É obrigatório que todos os integrantes tenham a aplicação instalada?

    O projeto pode ser investigado em equipe. Ter pelo menos uma máquina funcionando facilita os testes, mas todos os integrantes devem participar da análise e compreender as conclusões. A execução local pode ser complementada por inspeção no GitHub e resultados demonstrativos, quando necessário e permitido pelas instruções do Moodle.

  • Posso corrigir o código assim que encontro uma suspeita?

    Na fase inicial, priorize documentar a revisão manual e preservar o commit original. Isso permite comparar o estado vulnerável e o corrigido. Implementar mudanças antes de registrar a linha de base pode apagar evidências e dificultar a comparação. As correções fazem parte das etapas finais.

  • Tenho que encontrar todas as vulnerabilidades deliberadas?

    A avaliação exige investigação fundamentada e documentação coerente, não uma contagem de adivinhações. Verifique a rubrica e as regras do Moodle. Identificar uma hipótese corretamente e explicar a limitação da evidência faz parte do trabalho técnico.

  • Se Semgrep não mostrar alerta, posso afirmar que o código é seguro?

    Não. Um SAST atua conforme as regras, modelos e arquivos analisados. Ausência de alerta pode indicar que determinado padrão não foi encontrado, mas não garante ausência de falhas de autorização, de lógica de negócio ou de outros tipos.

  • E se o CodeQL não estiver disponível no meu repositório privado?

    O plano gratuito do GitHub pode não incluir Code Scanning/CodeQL para repositórios privados. Utilize a alternativa definida nas orientações do Moodle, como resultados de uma demonstração em repositório público. Identifique claramente a origem dos dados. Não é correto afirmar que uma análise foi executada localmente se a equipe apenas interpretou um relatório fornecido.

  • Posso usar ferramentas de IA?

    Sim, nas condições definidas pelo protocolo da disciplina, após preservar a revisão manual independente. Registre a ferramenta, os prompts, as respostas e a verificação feita. Não compartilhe segredos, tokens, .env ou dados reais. A IA sugere hipóteses; as evidências e decisões técnicas são responsabilidade da equipe.

  • Preciso fazer upload dos seis arquivos de etapa no Moodle?

    Não como seis avaliações independentes. O percurso possui registros intermediários, mas duas entregas formais estão previstas: revisão manual parcial e auditoria final integrada. O Moodle especifica o que deve ser anexado em cada uma. Os registros intermediários ajudam a organizar as evidências que serão utilizadas nelas.

  • Se eu fizer commit no GitHub, a entrega está concluída?

    Não necessariamente. O código e o histórico ficam no GitHub; a submissão oficial ocorre no Moodle. Verifique qual atividade está aberta, o formato exigido e o prazo informado na oferta. Envie o arquivo/link conforme solicitado e confira se o envio foi registrado.

  • Qual é a diferença entre hipótese e vulnerabilidade confirmada?

    A hipótese é uma possibilidade fundamentada que ainda precisa de verificação. Um achado confirmado apresenta evidências suficientes de que uma condição viola um requisito de segurança. A conclusão deve informar os limites do que foi testado; um indício visual em uma função isolada pode não ser suficiente.

  • Devo usar a quantidade de alertas como medida de qualidade da ferramenta?

    Não. O volume de alertas isoladamente não mede precisão, revocação, gravidade nem utilidade. Investigue alertas duplicados, alcance, falsos positivos, lacunas de detecção e os critérios de configuração antes de comparar métodos.

  • E se a minha correção fizer o teste de segurança passar, mas quebrar uma funcionalidade legítima?

    Essa alteração introduz uma regressão. É necessário verificar tanto o comportamento proibido quanto o comportamento permitido. A revisão deve explicar o que mudou, por que a correção respeita os requisitos e quais testes sustentam a conclusão.

  • Posso usar dados reais ou publicar o laboratório na internet para facilitar o acesso?

    Não. A API possui vulnerabilidades intencionais para treinamento. Mantenha execução local e isolada, use dados fictícios, preserve o repositório privado da equipe e não compartilhe chaves ou dados pessoais reais.

  • Preciso alterar o package.json ou instalar Prisma/TypeScript globalmente?

    Não para a configuração básica. O projeto contém seus scripts e dependências. Instale os pré-requisitos de sistema, depois execute os comandos previstos no README. As dependências de aplicação são instaladas no próprio projeto.

  • Uma resposta gerada por IA pode ser usada como evidência empírica?

    Não, isoladamente. A IA pode levantar hipóteses e ajudar a organizar testes. Para afirmar que uma vulnerabilidade foi reproduzida, documente o código e/ou a execução realizada. Se o teste não foi executado, declare essa limitação.
