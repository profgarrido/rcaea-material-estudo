Como acessar e utilizar o GitHub no laboratório

Preparar a conta, ingressar na equipe, clonar o repositório, registrar evidências e distinguir o trabalho no GitHub da entrega formal.

O papel do GitHub no laboratório

O código da sua equipe, em um lugar organizado

Ao longo da disciplina, sua equipe analisará uma aplicação em Node.js e TypeScript, registrará hipóteses e achados, utilizará ferramentas de análise estática, comparará resultados e documentará as correções que conseguir validar. Esse trabalho precisa ficar organizado e ser rastreável: outra pessoa deve conseguir descobrir o que foi analisado, em qual versão, quem registrou a mudança e quais evidências sustentam a conclusão.

É para isso que vamos utilizar o GitHub. Cada equipe terá acesso a um repositório privado, com uma cópia inicial da API do laboratório. Os integrantes poderão consultar o mesmo código, registrar arquivos Markdown, trabalhar em branches, propor mudanças por Pull Requests e consultar o histórico de commits.

O GitHub não substitui as aulas nem o ambiente de entrega formal. Cada ambiente tem uma responsabilidade diferente:

Página da disciplina (GitHub Pages)

Estudar os conteúdos, consultar o guia e seguir os procedimentos do laboratório. Não recebe nota, código ou relatórios enviados por formulário.

GitHub da equipe

Guardar código, análises, evidências, commits, branches e Pull Requests. Não substitui a submissão exigida no Moodle.

Moodle

Consultar materiais liberados, prazos, orientações oficiais e atividades de entrega. Não substitui o histórico técnico do repositório.

Em resumo: você estuda na página, trabalha no GitHub e entrega pelo Moodle. Os três ambientes se complementam.

O percurso do seu primeiro acesso

O caminho será: preparar a conta → informar o username → receber convite → ingressar na organização e na equipe → abrir repositório → clonar, se for executar localmente → trabalhar e registrar evidências.

Se o primeiro acesso ainda não estiver liberado, não significa que você cometeu algum erro: o repositório é privado e depende da autorização da organização. Enquanto isso, você pode preparar o Git, Node.js, Docker e editor, além de consultar os materiais públicos da disciplina.

Git, GitHub, organização, Team e repositório

É comum tratar Git e GitHub como sinônimos, mas eles cumprem papéis diferentes.

Git

Sistema de controle de versões para registrar mudanças em arquivos. Permite criar commits, comparar versões, trabalhar em branches e recuperar alterações. A maior parte das operações ocorre no computador, mesmo sem internet.

GitHub

Plataforma que hospeda repositórios Git e acrescenta ferramentas de colaboração: Pull Requests, discussões, revisão de código e controle de acesso. A sincronização ocorre por git push e git pull.

Organização

Espaço administrativo que reúne vários repositórios e controla os acessos. Neste laboratório: appsec-labs-cesar-school.

Team

Grupo de membros da organização. Quando você entra no Team correto, herda o acesso aos repositórios atribuídos àquele grupo, conforme o papel concedido.

Repositório

Conjunto versionado de arquivos e histórico. O repositório privado da sua equipe contém o código inicial e será o espaço de trabalho do grupo. Um repositório privado não aparece para quem não tem permissão.

GitHub Pages

Funcionalidade usada para publicar este site de estudo. Ele é público e tem finalidade diferente dos repositórios privados do laboratório.

No desenho, A e B são apenas exemplos. Você não precisa criar a organização, o Team ou o repositório. Essas estruturas serão disponibilizadas para seu grupo.

O que a permissão Write permite

O acesso Write permite colaborar no repositório: criar branches, enviar commits, propor Pull Requests e modificar arquivos conforme as regras do projeto. Não é uma permissão de administração. Alterar acesso de outros usuários, excluir repositórios ou mudar determinadas configurações é responsabilidade de quem os administra.

Uma pessoa pode conhecer o endereço de um repositório privado e ainda assim não conseguir abri-lo. Saber o nome de um repositório não equivale a ter permissão de acesso.

Prepare sua conta GitHub

1. Criar ou acessar a conta

Abra github.com e entre na sua conta. Se ainda não tiver uma, escolha Sign up e siga as instruções do GitHub para criar e verificar a conta.

Utilize uma conta pessoal que você consiga acessar durante as aulas e depois delas. Se já utiliza GitHub profissionalmente, não é necessário criar uma segunda conta, a menos que isso faça sentido para suas próprias restrições de uso.

2. Identificar seu username

O username é o identificador de sua conta no GitHub, não seu nome completo nem seu e-mail. Para localizá-lo, clique na foto de perfil e observe o identificador exibido no menu. Outra forma é abrir seu perfil e consultar a URL:

https://github.com/SEU_USERNAME

Exemplo fictício: se o perfil fosse https://github.com/aluno-exemplo, o username seria aluno-exemplo.

A equipe deverá informar os usernames conforme a orientação do Moodle ou do responsável pela organização. Digitar o nome completo em vez do username pode impedir que o convite seja enviado à conta correta.

3. Conferir o e-mail e a autenticação de dois fatores

Verifique se você consegue receber notificações e convites no e-mail associado à sua conta. Considere também o ambiente de segurança exigido pelo GitHub: contas que contribuem com código podem precisar habilitar autenticação de dois fatores (2FA), e organizações podem exigir essa configuração para seus membros.

Se o GitHub pedir configuração de 2FA, conclua o processo pela página oficial de segurança da sua conta. Guarde os métodos de recuperação em local seguro. Nunca compartilhe códigos de autenticação nem códigos de recuperação com colegas.

4. Conferência antes da aula prática

Você está preparado para solicitar acesso quando conseguir confirmar estes quatro pontos:

  1. Consegue entrar em github.com.
  2. Conhece o username correto da sua conta.
  3. Consegue acessar as notificações e e-mails de convite.
  4. Sabe qual é a equipe atribuída ao seu grupo, conforme a organização realizada na disciplina.

Não é necessário enviar senha, token ou código de autenticação ao docente ou aos colegas.

Como entrar na organização e no Team da sua equipe

O ingresso não é automático por um link

A organização do laboratório utiliza Teams privados de trabalho, associados a repositórios específicos. Você não entra automaticamente em um Team por abrir o endereço do GitHub ou compartilhar uma URL de equipe. A inclusão exige uma ação de quem administra a organização ou um processo oficial de convite.

Assim, o link da organização serve para identificar o ambiente, mas não substitui o convite. Da mesma forma, se o colega já entrou, isso não significa que você terá acesso sem ser incluído.

Passo 1. Informe o username da conta correta

Depois de definir sua equipe segundo as orientações da disciplina, informe seu username GitHub pelo canal estabelecido no Moodle ou em aula. Confirme as letras, números e hífens. Se você usa mais de uma conta, informe aquela em que estará autenticado para trabalhar.

Passo 2. Aguarde o convite administrativo

A pessoa responsável pela organização adicionará sua conta ao Team apropriado ou enviará um convite para ingresso na organização. Dependendo de sua situação, você poderá receber uma mensagem por e-mail, uma notificação no GitHub ou um convite indicado no fluxo da organização.

O tempo de liberação depende dessa inclusão. Antes dela, receber um erro ao abrir um repositório privado não prova que o endereço está incorreto.

Passo 3. Aceite o convite no GitHub

Abra o convite recebido e confirme que o destino é o GitHub oficial, com domínio github.com. Esteja conectado com o mesmo username informado. Leia o nome da organização e aceite o ingresso caso corresponda à atividade da disciplina.

Se a organização exigir 2FA, pode ser necessário habilitá-la antes de concluir a aceitação. Se o convite não aparecer, confira as notificações da conta, o e-mail cadastrado e a caixa de spam. Não crie outra conta sem antes verificar se você informou o username correto.

Passo 4. Confirme a participação na equipe

Depois da aceitação, acesse a organização appsec-labs-cesar-school. Verifique se consegue localizar o repositório da sua equipe por meio do link fornecido no Moodle. Se a organização permitir a visualização da lista de Teams, você também poderá consultar sua participação por lá.

Importante: participar da organização e fazer parte do Team correto são informações relacionadas, mas distintas. Se você consegue ver a organização e não consegue abrir o repositório da sua equipe, informe o username e a equipe ao responsável pela configuração; talvez sua inclusão no Team ainda esteja pendente.

Passo 5. Confirme com seus colegas

Cada integrante deve abrir o mesmo repositório da equipe na própria conta. Não utilizem uma única conta compartilhada. Trabalhar com contas individuais faz com que commits, comentários e Pull Requests sejam atribuídos corretamente a quem os realizou.

Como encontrar o repositório privado da sua equipe

O endereço certo é o que foi atribuído ao grupo

Cada equipe trabalhará sobre uma cópia própria da aplicação. Utilize o link indicado no Moodle ou fornecido pelo responsável pela organização. Não tente descobrir repositórios privados alterando o número de outros grupos na URL.

O endereço de um repositório do GitHub normalmente segue este formato:

https://github.com/ORGANIZACAO/NOME_DO_REPOSITORIO

Neste laboratório, a organização é conhecida; já o nome efetivo do repositório da sua equipe deverá ser confirmado no GitHub ou no Moodle, pois pode variar entre ofertas da disciplina.

Reconhecendo a tela correta

Ao abrir um repositório para o qual você tem permissão, verá uma página com o nome do projeto, abas como Code, Issues e Pull requests, uma lista de arquivos e o histórico de commits. A aparência exata pode variar com atualizações da interface.

Antes de começar, verifique:

  • O nome do repositório corresponde à sua equipe.
  • A organização exibida é appsec-labs-cesar-school.
  • Você consegue visualizar README.md, package.json, src/, prisma/ e docs/.
  • Seus colegas também têm acesso ao mesmo repositório.

A cópia inicial não deve ser substituída por um repositório público criado individualmente. Nosso trabalho utiliza o repositório privado da equipe para preservar o contexto da atividade e as evidências da investigação.

Clonar o repositório: trazer o projeto para seu computador

O que significa clonar?

Clonar é obter uma cópia local de um repositório Git, incluindo seus arquivos e seu histórico de versões. A partir dessa cópia, você poderá executar a API, criar branches, fazer commits e enviar mudanças para o GitHub.

Clonar não é criar um novo repositório e não remove o original. Cada integrante pode ter uma cópia local, mas todos deverão enviar o trabalho para o repositório privado compartilhado da equipe.

Antes de clonar

É necessário ter Git, Node.js e Docker instalados no seu computador. Se ainda não preparou o ambiente, consulte o guia de preparação do ambiente antes de prosseguir.

É necessário também estar autorizado a acessar o repositório. Verifique a instalação do Git em um terminal:

git --version

Se o comando não for reconhecido, instale o Git pela página oficial e reinicie o terminal.

Método A. Clonagem pelo terminal

  1. Abra o repositório privado no navegador, autenticado no GitHub.
  2. Na página do repositório, clique em Code.
  3. Selecione HTTPS e copie a URL exibida.
  4. Abra o terminal na pasta de seu computador onde deseja guardar o projeto.
  5. Execute git clone seguido da URL que você acabou de copiar:
git clone URL_HTTPS_COPIADA_NO_GITHUB
Atenção: não digite literalmente URL_HTTPS_COPIADA_NO_GITHUB. Substitua pelo endereço copiado do botão Code. Esse endereço é exclusivo do repositório escolhido e não deve ser presumido pelo guia público.

Entre na pasta recém-criada:

cd NOME_DA_PASTA_CLONADA

Confira se o projeto foi clonado:

git status
git remote -v

git status indica o estado de sua cópia local. git remote -v mostra o endereço do repositório remoto configurado, normalmente identificado como origin.

Como funciona a autenticação

Ao clonar um repositório privado por HTTPS, o Git pode abrir uma janela de autenticação no navegador. No Windows, o Git Credential Manager, disponível em instalações atuais de Git para Windows, permite utilizar esse fluxo e guardar credenciais de maneira apropriada.

O GitHub não aceita a senha comum da conta como senha para operações Git por HTTPS. Se aparecer uma solicitação de senha no terminal, não continue tentando a senha da página web. Utilize um gerenciador de credenciais, GitHub CLI ou o método de autenticação configurado para sua máquina.

Se você já utiliza SSH, também pode clonar pelo endereço SSH do botão Code, desde que sua chave pública esteja cadastrada no GitHub. Não é necessário configurar SSH para acompanhar este laboratório.

Método B. GitHub Desktop

Quem preferir uma interface gráfica pode utilizar GitHub Desktop:

  1. Instale o aplicativo e autentique-se com sua conta GitHub.
  2. No repositório privado, abra Code e escolha a opção de abrir com GitHub Desktop, se estiver disponível, ou utilize File → Clone repository no aplicativo.
  3. Escolha uma pasta local e conclua a clonagem.
  4. Confirme que o aplicativo está conectado ao repositório da equipe.

O GitHub Desktop facilita a clonagem, a criação de commits e o push. Para executar a API, entretanto, você ainda utilizará um terminal e os scripts npm.

Posso trabalhar apenas pelo navegador?

Você poderá ler o código e editar arquivos Markdown diretamente na interface do GitHub, conforme suas permissões. Essa opção é útil quando o computador não está preparado para executar a API. Contudo, editar pelo navegador não equivale a executar o software nem a comprovar um teste de segurança. Registre corretamente a origem das evidências e utilize um equipamento da equipe para as verificações que exigem execução local.

Preparar e executar a API localmente

Pré-requisitos reais do laboratório

A API utiliza Node.js, TypeScript, Express, Prisma, PostgreSQL e JWT. O projeto-base foi preparado para Node.js 20.19.0 ou superior. Não é necessário instalar TypeScript, Prisma CLI ou PostgreSQL separadamente.

GitClonar e versionargit --version
Docker com ComposeExecutar o PostgreSQL localdocker compose version e docker info

No Windows, o Docker Desktop deve estar aberto e com seu Engine funcionando. Instalar Docker sem iniciá-lo não basta para executar o PostgreSQL.

Preparação inicial

Na pasta que contém o package.json, execute:

npm run doctor

O comando analisa a disponibilidade de Node.js, npm, Git, Docker e Compose, além de condições necessárias à preparação do ambiente. Se indicar que falta algum componente, corrija a condição indicada antes de continuar.

Depois, execute:

npm run setup

O setup instala dependências, prepara um arquivo .env local com chave JWT, inicia o PostgreSQL pelo Docker, gera o Prisma Client, aplica as migrations e insere dados fictícios para a investigação. Ele foi criado para simplificar a primeira execução da equipe.

Quando o processo terminar sem erros, execute:

npm run dev

O servidor Express ficará em execução no terminal. Abra outro terminal caso precise executar novos comandos.

Como verificar que a API respondeu

No navegador, acesse:

http://127.0.0.1:3000/health

A resposta esperada da aplicação é:

{
  "status": "ok",
  "environment": "laboratory"
}

Esse resultado demonstra que o endpoint de saúde está respondendo. Ele não prova que todas as funcionalidades estão corretas nem que a API está segura. Para verificar integração com banco e autenticação, siga também os exemplos e contas fictícias do README.md do seu repositório privado e as requisições em docs/requests.http.

Testes básicos e compilações

Os scripts de verificação disponíveis incluem:

npm run build
npm run test:smoke

npm run build verifica se o projeto TypeScript compila. npm run test:smoke executa testes funcionais básicos de conectividade e autenticação. A presença desses testes não significa que todas as vulnerabilidades intencionais do laboratório foram identificadas ou corrigidas.

Execuções seguintes

Nas aulas seguintes, você pode utilizar:

npm run lab

Esse script verifica ou inicia o banco e a API conforme a configuração do projeto. Para parar os containers do laboratório sem apagar o volume do PostgreSQL:

npm run db:stop

Evite docker compose down -v e prisma migrate reset sem orientação, pois esses comandos podem eliminar dados locais.

Se a equipe não conseguir executar localmente

O objetivo da disciplina é auditar o código, não avaliar a instalação de infraestrutura. Quando um computador não atender aos pré-requisitos, a equipe pode organizar uma máquina principal para os testes e utilizar as demais para revisão de código, pesquisa e documentação. Se nenhuma máquina executar a API, registrem a dificuldade e utilizem os resultados demonstrativos disponibilizados pela disciplina, quando houver.

Atenção: não declarem que executaram um teste que não foi executado. Diferenciem sempre "observado localmente", "observado em demonstração", "inferido por leitura" e "ainda não verificado".

Entender o Git antes de registrar alterações

O que muda quando você edita um arquivo

Ao clonar o repositório, seu computador tem uma cópia de trabalho. Se você editar README.md ou criar um arquivo de registro, a mudança existe inicialmente apenas na máquina. Para torná-la parte do histórico compartilhado, você precisa passar por algumas etapas:

Arquivo na pasta local
       │ editar
       ▼
Working tree: mudanças ainda não registradas
       │ git add
       ▼
Staging area: arquivos selecionados para o commit
       │ git commit
       ▼
Histórico local: commit identificado por hash
       │ git push
       ▼
Repositório remoto no GitHub
       │ abrir Pull Request, quando aplicável
       ▼
Revisão de mudanças e eventual integração

O commit é um registro de uma alteração no histórico Git, com identificador próprio. O push envia commits locais para o repositório remoto. O Pull Request é uma proposta de incorporar mudanças entre branches, acompanhada de contexto e revisão. Esses conceitos se complementam, mas não são a mesma ação.

Configure sua identificação no Git

Na primeira utilização de Git em seu computador, você pode configurar o nome e o e-mail que aparecerão como autor dos commits:

git config --global user.name "SEU_NOME_DE_EXIBICAO"
git config --global user.email "SEU_EMAIL_DE_COMMITS"

Substitua os valores por seus dados apropriados. O GitHub permite utilizar um endereço de e-mail privado do tipo noreply nas configurações da conta. Não use o e-mail ou a conta de um colega como identidade do commit.

Para conferir:

git config --global user.name
git config --global user.email

Verificar o estado de sua cópia

git status

O resultado mostrará a branch atual, arquivos alterados e arquivos ainda não rastreados. Antes de qualquer commit, examine essa lista e tenha certeza de que ela contém apenas o material que deve ser versionado.

Cuide de arquivos locais

O arquivo .env contém configurações de execução e pode incluir credenciais ou segredos de treinamento. Ele não deve ser enviado para o GitHub. node_modules/, dist/, arquivos de log e dados temporários também não devem ser incluídos no repositório.

O projeto já possui .gitignore. Mesmo assim, examine git status e, sobretudo, git diff --cached antes de confirmar um commit. O .gitignore não remove automaticamente arquivos que já foram versionados anteriormente.

Trabalhar em branches sem perder a linha de base

Por que não alterar tudo diretamente em main?

A branch main representa a linha principal do repositório da equipe. Uma branch de trabalho permite separar uma tarefa, registrar seus commits e apresentar a mudança para revisão antes da integração. Isso ajuda a organizar o laboratório, no qual a revisão manual precisa ser preservada antes das ferramentas automatizadas e das correções.

No GitHub Free, a utilização de Pull Requests e branches pode ocorrer por convenção da equipe, mesmo quando o plano não oferece a imposição automática de todas as regras de proteção de branch em repositórios privados. A ausência de uma proteção automática não dispensa a revisão acordada pelo grupo.

Exemplo completo: registrando o inventário inicial

Primeiro, confirme que está na pasta do repositório e que não há alterações locais inesperadas:

git status

Se sua branch main local estiver sem alterações e sua equipe não estiver fazendo uma mudança concorrente, atualize-a:

git switch main
git pull --ff-only origin main

O uso de --ff-only evita criar automaticamente um commit de merge quando o histórico local diverge. Se o comando falhar, não faça reset --hard para "resolver" o problema: identifique a divergência com a equipe.

Crie uma branch para o registro inicial:

git switch -c docs/inventario-inicial

Crie o arquivo entregas/01_inventario.md no editor, seguindo as orientações da etapa correspondente do laboratório. Se a pasta ainda não existir, crie-a. Depois confira e prepare apenas esse arquivo:

git status
git add entregas/01_inventario.md
git diff --cached

O último comando mostra o conteúdo selecionado para o próximo commit. Leia-o antes de registrar a mudança.

Quando estiver correto:

git commit -m "docs: registra inventario inicial"
git push -u origin docs/inventario-inicial

O commit ficará registrado localmente e depois será enviado para uma branch remota no repositório da equipe. Para visualizar o histórico:

git log --oneline -5

Os identificadores apresentados nesse histórico servem para relacionar evidências à versão do código analisado.

E se o colega já alterou arquivos?

Conversem sobre qual mudança será integrada primeiro. É comum que duas pessoas editem o mesmo documento; nesse caso, o Git pode exigir uma resolução manual de conflito. O conflito não significa perda automática de dados: significa que existem duas alterações que precisam ser reconciliadas antes de seguir.

Não use git push --force ou git reset --hard para contornar conflitos sem compreender as consequências e sem combinar com os integrantes. Esses comandos podem sobrescrever ou descartar trabalho.

Abrir Pull Requests e revisar alterações

O Pull Request é uma explicação, não apenas um botão

Um Pull Request, ou PR, apresenta a diferença entre duas branches e abre um espaço para revisão. Ele permite explicar qual problema motivou a mudança, o que foi modificado e como verificar o resultado.

Em um laboratório de revisão de código, o PR tem valor pedagógico especial: outra pessoa precisa interpretar o contexto, identificar riscos, comentar sobre as evidências e decidir se a mudança está suficientemente justificada.

Como abrir um PR

  1. Crie uma branch e faça push de seus commits para o repositório da equipe.
  2. Abra o repositório no GitHub.
  3. Acesse a aba Pull requests e escolha New pull request, ou utilize a opção Compare & pull request, quando aparecer.
  4. Em base, selecione a branch que receberá a mudança, normalmente main.
  5. Em compare, selecione sua branch de trabalho.
  6. Leia o resumo de arquivos e as diferenças exibidas em Files changed.
  7. Escreva um título objetivo e uma descrição que permita revisar a proposta.
  8. Crie o PR e solicite a revisão de um integrante, quando possível.
  9. Discuta os comentários e acrescente novos commits na mesma branch caso seja necessário ajustar algo.
  10. Integre a alteração somente depois de compreender seus impactos e de acordo com o fluxo combinado pela equipe.

Modelo de descrição de PR

## Objetivo
Registrar o inventário inicial do laboratório e as hipóteses de inspeção.

## O que foi alterado
- Criado `entregas/01_inventario.md`.
- Organizadas rotas, módulos e requisitos a verificar.
- Indicada a versão do código de referência.

## Como verificar
1. Abrir o documento Markdown.
2. Conferir a correspondência com os requisitos de negócio.
3. Verificar se as hipóteses estão separadas dos achados confirmados.

## Limitações
- Não foram executadas ferramentas SAST nesta etapa.
- Hipóteses ainda dependem de inspeção complementar.

## Revisão solicitada
Conferir a precisão do inventário e a rastreabilidade das hipóteses.

Como comentar de forma útil

Compare dois comentários fictícios sobre um arquivo de requisitos:

Comentário pouco útil: "Isso está errado. Precisa melhorar."

Comentário fundamentado: "O registro afirma que a rota exige autorização por recurso, mas ainda não identifica onde essa regra é aplicada. Você consegue acrescentar o arquivo/função verificado e explicar se a conclusão veio de leitura, teste ou hipótese?"

O segundo comentário permite que quem escreveu saiba o que investigar e qual evidência falta. A revisão deve analisar o conteúdo da proposta, não apenas confirmar que o arquivo existe.

Revisão de código não é automaticamente aprovação de segurança

Um PR aprovado indica que a mudança passou por uma revisão no escopo daquele processo. Não é prova de que a aplicação inteira está segura. Testes e ferramentas automatizadas também têm cobertura limitada. Durante a auditoria, descreva quais verificações realmente ocorreram e quais limitações permanecem.

Como escrever uma evidência verificável

Evite registros como "encontramos uma vulnerabilidade na API". Essa frase não permite que alguém reproduza ou compreenda sua conclusão.

Um achado deve apresentar pelo menos: requisito relacionado, arquivo/função, versão do código ou commit, condição investigada, comportamento esperado, comportamento observado, origem da observação, impacto possível, situação da hipótese e recomendação. Evidências podem incluir testes negativos controlados, trechos de código contextualizados e saídas de ferramentas identificadas.

Exemplo neutro, independente da API avaliada:

### Hipótese H-01: autorização no compartilhamento de documentos

- Requisito: somente pessoas autorizadas podem compartilhar documentos.
- Fluxo: rota de compartilhamento → service → repository.
- Referência: commit <HASH_DA_VERSAO_ANALISADA>.
- Observação: a rota autentica o usuário, mas ainda precisamos verificar
  se a autorização por documento é aplicada na camada de serviço.
- Classificação: hipótese, não confirmada.
- Próximo passo: revisar o service e executar teste negativo com
  um usuário que não seja proprietário, em ambiente controlado.

O exemplo ilustra a diferença entre hipótese e confirmação. Não representa uma vulnerabilidade identificada no projeto real da disciplina.

Por que registrar o commit?

O código muda durante o projeto. Uma hipótese registrada hoje pode deixar de ser verdadeira depois de uma correção ou refatoração. O hash do commit permite localizar o estado exato em que a observação foi feita. Por isso, preserve uma linha de base da revisão manual antes de incorporar resultados de Semgrep, CodeQL ou IA e antes de alterar trechos investigados.

Posso colar o resultado de uma ferramenta como relatório?

A saída de uma ferramenta é uma fonte de evidência, não uma conclusão completa. Explique a regra utilizada, os arquivos analisados, a versão da ferramenta, o contexto do alerta, as condições de risco, as verificações realizadas e a justificativa da classificação. Não use apenas capturas de tela. Se a ferramenta não foi executada no ambiente da equipe, identifique expressamente a origem dos resultados fornecidos.

Como registrar o trabalho em equipe

Distribuam atividades e documentem a revisão cruzada, sem exigir que todos realizem exatamente a mesma alteração. O histórico de commits e os comentários dos PRs podem ajudar a demonstrar como a equipe trabalhou e discutiu as decisões técnicas. Evitem fazer todo o projeto em uma conta compartilhada, pois isso torna a autoria e a rastreabilidade menos claras.

O que registrar no GitHub e o que entregar no Moodle

O projeto é contínuo, mas as entregas formais são duas

O trabalho ocorre em seis etapas integradas. Em cada uma delas, o grupo produz registros que permanecem versionados no GitHub. Entretanto, existem apenas duas entregas formais, conforme as atividades oficiais do Moodle:

  1. Revisão manual parcial, associada à terceira etapa. A evidência central é entregas/02_revisao_manual.md, contendo a análise humana preservada antes das ferramentas automatizadas.
  2. Auditoria integrada final, associada à sexta etapa. A evidência central é o relatório consolidado entregas/06_relatorio_final.md, com resultados dos métodos utilizados, comparação, correções selecionadas, verificações e riscos residuais.

Os arquivos intermediários são necessários para documentar a evolução técnica, mas não exigem uma submissão formal independente no Moodle a cada etapa, salvo orientação institucional adicional.

Como concluir uma entrega formal

  1. Verifique se os arquivos exigidos estão no repositório privado da equipe e se o histórico correspondente foi enviado ao GitHub.
  2. Abra os links ou arquivos na própria interface do GitHub para conferir se são legíveis.
  3. Identifique o commit ou a versão a que o relatório se refere. Confirme que não está enviando uma branch antiga ou um documento ainda incompleto.
  4. Consulte a atividade correspondente no Moodle, leia formato, prazo e anexos solicitados.
  5. Submeta o arquivo e/ou o link solicitado pelo Moodle. O que vale como submissão é o registro na atividade oficial, não apenas a existência de um commit.
  6. Verifique a confirmação de envio no Moodle.
GitHub registra o trabalho. Moodle recebe a entrega. Uma ação não substitui automaticamente a outra.

Cuidados de segurança durante o trabalho

Repositório privado não significa ausência de cuidados

A aplicação-base contém situações intencionalmente inseguras para fins de aprendizagem. Execute-a apenas em ambiente de treinamento, com dados fictícios e acesso restrito. Não hospede a API vulnerável publicamente, não exponha suas portas à internet e não reutilize configurações de laboratório em sistemas reais.

O que não colocar em commits ou PRs

  • Senhas de contas pessoais, tokens de autenticação e códigos de recuperação.
  • Conteúdo do .env, chaves JWT, credenciais de serviços ou segredos de integração.
  • Capturas de tela que exibam informações privadas da conta ou dados pessoais de terceiros.
  • Informações confidenciais de empresas, projetos reais ou sistemas fora do escopo do laboratório.
  • Resultados de varredura sobre serviços que não façam parte da atividade autorizada.

Utilize dados fictícios e redija valores sensíveis em logs e imagens. Se um segredo for enviado por engano a um commit, apenas excluí-lo no commit seguinte pode não removê-lo do histórico. Informe o ocorrido imediatamente aos responsáveis pelo ambiente e providencie a revogação do segredo afetado.

Ao utilizar ferramentas de IA

Não compartilhe tokens, .env, credenciais ou dados reais com assistentes externos. Se utilizar IA para apoiar análise de código, registro de hipóteses ou revisão, indique ferramenta, finalidade, informações fornecidas e validação independente. Respostas de IA não são evidência de testes executados.

Ao trabalhar com colegas

Utilizem suas próprias contas e permissões. Não solicitem login ou 2FA do colega. Não concedam acesso ao repositório para pessoas externas à equipe sem autorização. Ao editar ou integrar um PR, preservem o histórico da investigação e os registros necessários à avaliação.

Problemas frequentes e como resolver

Recebo erro 404 ao abrir o repositório da equipe

Em repositórios privados, um 404 pode indicar falta de permissão, não necessariamente a inexistência do endereço. Verifique se está autenticado com o username convidado, se aceitou o convite da organização, se foi incluído no Team correto e se recebeu o link oficial do repositório. Se os colegas conseguirem abrir e você não, informe seu username e a equipe para conferência administrativa.

Aceitei o convite, mas ainda não consigo abrir o repositório

Confirme primeiro se o convite de organização foi aceito e, depois, se houve inclusão no Team que tem acesso ao repositório. Essas duas condições são distintas. Evite criar outra conta ou duplicar o repositório para contornar a permissão: isso fragmentaria as evidências do grupo.

Não recebi o e-mail de convite

Confira o e-mail associado à conta GitHub, notificações, spam e o username informado. O convite também pode estar pendente de ações na própria conta. Se persistir, solicite conferência do convite ao responsável pela organização, sem compartilhar senha ou código de segurança.

O Git pede uma senha que não funciona

O GitHub não aceita a senha normal de login para operações Git por HTTPS. Utilize o fluxo de autenticação do Git Credential Manager ou GitHub CLI, ou SSH se já configurado. Evite criar tokens de acesso pessoal sem compreender o escopo e a necessidade. Nunca cole credenciais em mensagens, documentos ou capturas de tela.

O comando git clone diz "Repository not found"

Confirme a URL copiada pelo botão Code, a autenticação na conta correta e o acesso ao repositório privado. Se o caminho estiver correto e a mensagem persistir, a causa pode ser autorização ausente ou credencial local de outra conta.

O comando git push retorna "Permission denied" ou erro 403

Verifique se o repositório remoto (git remote -v) corresponde ao da sua equipe, se a conta autenticada é a autorizada e se você possui permissão Write. Para corrigir, procure a configuração de credenciais ou a pessoa responsável pela organização. Não solicite permissão de administrador para executar operações comuns de estudante.

Não consigo fazer push porque o repositório remoto tem commits novos

O repositório pode ter recebido alterações de um colega. Veja git status, git branch --show-current e converse com a equipe sobre como sincronizar as branches. Não resolva esse caso executando git push --force, git reset --hard ou apagando a pasta sem compreender a situação.

Apareceu um conflito de merge

Um conflito significa que o Git não consegue decidir sozinho como combinar determinadas alterações. Abra os arquivos indicados, compare as versões e discuta o resultado correto com quem editou o material. Remova marcadores de conflito somente depois de decidir qual conteúdo manter, execute os testes pertinentes e registre a resolução. Em caso de dúvida, preserve o trabalho local e peça orientação antes de descartar mudanças.

node ou npm não é reconhecido

Confira se Node.js está instalado e se a versão é pelo menos 20.19.0. Abra um novo terminal após a instalação e execute node -v e npm -v. Se o problema persistir, investigue a configuração de PATH ou utilize o computador de outro integrante que esteja preparado.

docker --version funciona, mas npm run setup falha

O cliente Docker pode estar instalado enquanto o Docker Engine está parado. Verifique docker info e docker compose version. No Windows, abra o Docker Desktop e aguarde o Engine iniciar. Não habilite configurações administrativas inseguras para contornar restrições do equipamento.

A porta 3000 ou a porta do banco está ocupada

Outra aplicação ou container pode estar utilizando a porta. Identifique o processo antes de encerrá-lo. Se for necessário alterar configuração, mantenha coerência entre .env, scripts e Compose, seguindo o guia de instalação da API e as orientações da equipe. Não publique uma porta externa como solução improvisada.

O endpoint /health funciona. A atividade está concluída?

Não. O endpoint /health confirma uma parte da inicialização. O objetivo do projeto é investigar requisitos, controles de acesso, fluxo de dados, resultados de ferramentas, correções e evidências. Um resultado funcional não equivale a uma auditoria de segurança.

O colega registrou um arquivo, mas não o vejo no meu computador

O colega precisa confirmar que fez git commit e git push, e você precisa obter as alterações do remoto na branch apropriada. Consulte o GitHub no navegador para identificar onde o commit foi enviado. Depois sincronize com cuidado, preservando quaisquer mudanças locais ainda não registradas.

Criei um commit, mas ele não aparece no GitHub

O commit pode existir apenas localmente. Execute git status, git log --oneline -5 e confira a branch atual. Se necessário, envie os commits com git push. Lembre-se: git commit registra localmente; git push envia ao remoto.

Abri um Pull Request. Isso já conta como entrega no Moodle?

Não. Pull Requests ajudam a explicar e revisar as mudanças. As entregas formais continuam sendo feitas nas atividades oficiais do Moodle, com os documentos e links exigidos. Sempre confira a confirmação de submissão.

Posso fazer tudo diretamente na branch main?

É tecnicamente possível em alguns repositórios, mas não é o fluxo recomendado. Utilize uma branch para cada conjunto de mudanças, proponha um PR e preserve o histórico. Como determinados controles obrigatórios de branch não estão incluídos no GitHub Free para repositórios privados, parte dessa disciplina de trabalho depende do acordo entre os integrantes.

Minha equipe encontrou uma suspeita. Devemos corrigir imediatamente?

Não alterem o comportamento antes de registrar a observação e a versão analisada. A comparação entre revisão manual, SAST, CodeQL e IA depende de uma linha de base preservada. Primeiro documentem a hipótese e as evidências; a correção será realizada no momento correspondente do percurso do laboratório.

Posso disponibilizar o projeto em um repositório público?

Não. O material foi organizado para investigação em repositórios privados da organização, com falhas intencionais para estudo. Repositórios públicos, deploys externos e compartilhamento desnecessário do código contrariam essa finalidade e podem expor respostas ou comportamentos inseguros.

Como devo proceder se não tiver computador adequado?

É possível acompanhar a leitura do código e a documentação diretamente pelo GitHub, além de trabalhar com outro integrante que consiga executar a API localmente. Registre claramente o que foi observado em execução e o que foi inferido por leitura. O desafio é demonstrar qualidade da análise, não apenas realizar a instalação.
