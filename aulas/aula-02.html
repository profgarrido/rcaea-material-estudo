Warm-up · 12 minutos

Estar autenticado significa estar autorizado?

Referência histórica · First American Financial, 2019

Um problema de controle de acesso no sistema de documentos da First American Financial permitia acesso a documentos por URLs com identificadores previsíveis. A situação foi objeto de procedimentos da autoridade financeira de Nova York (NYDFS).

Atenção: exposição potencial não equivale a confirmação de que todos os documentos foram efetivamente acessados.

Você recebeu um link legítimo para consultar um documento. Ao modificar um número da URL, consegue visualizar um documento de outra pessoa.

O problema está no usuário que alterou o endereço, ou na aplicação que permitiu o acesso?

O que faltou verificar na API?

O sistema conhece Ana (autenticação), mas não verifica se Ana tem relação com o documento 1002 ou 1003 (autorização). A API deveria checar: este usuário pode acessar este recurso específico?, não apenas se está autenticado.

Autenticação no middleware não substitui autorização contextual. O service é o lugar típico para coordenar a regra de negócio; o repository pode reforçar com consultas corretamente restritas ao escopo autorizado.

Uma aplicação não é segura apenas porque sabe quem você é. Ela também precisa verificar o que você pode fazer. A partir daqui: revisão manual estruturada, IDOR/BOLA, fronteiras de confiança e regras de negócio.

Fundamentação teórica · 1

Revisar código significa reconstruir sua intenção

1

Contexto e intenção

O revisor de segurança procura compreender como dados, privilégios e estados atravessam componentes. A leitura começa no contexto da funcionalidade:

  • Requisitos da funcionalidade
  • Ativos protegidos e perfis de usuário
  • Decisões de acesso documentadas
→
2

Pontos críticos de execução

Em seguida identifica pontos de entrada, chamadas críticas e saídas observáveis.

  • Pontos de entrada e chamadas críticas
  • Saídas observáveis do sistema
  • Compilar, testar ou retornar o HTTP esperado não equivale a ser seguro.
03

A OWASP recomenda que o escopo da revisão manual inclua:

  • Arquitetura: decisões estruturais de segurança
  • Autenticação: como a identidade é verificada
  • Autorização: o que cada perfil pode fazer
  • Tratamento de erros: o que é exposto ao cliente
  • Lógica de negócio: regras de domínio implícitas
  • Fluxo de dados: como dados sensíveis transitam
04

Duas abordagens complementares estruturam a revisão de código e a auditoria de segurança (AppSec).

Baseline Review

Avalia a aplicação de modo abrangente. Usada em onboarding, auditorias periódicas e aquisição de sistemas legados.

Diff-based Review

Concentra-se nas linhas alteradas e na repercussão sobre controles existentes. Aplicada em Pull Requests e CI/CD.

Ver comparação completa
Critério

Diff-based Review
Escopo
Toda a base de código, configurações, dependências e arquitetura.
Apenas o delta (linhas adicionadas, removidas ou alteradas) e o contexto imediato.
Objetivo
Mapear a superfície de ataque total, encontrar dívidas técnicas e vulnerabilidades latentes.

Alto esforço; processo lento e profundo.

Como se conectam na prática:

  • A Baseline cria o alicerce: sem ela, uma revisão diff-based pode aprovar código aparentemente seguro que interage com arquitetura ou controle de acesso já comprometido na base.
  • O Diff mantém a integridade: estabelecida a linha de base, a revisão diff-based atua como barreira contínua para impedir a degradação ao longo do tempo.
05

Em um PR, o risco pode estar em:

  • Uma função modificada que introduz uma nova falha diretamente.
  • O contrato de uma função não alterada que passa a ser chamada em um contexto diferente.
Revisar apenas o "diff verde" sem conhecer as chamadas do código circundante pode deixar uma vulnerabilidade passar despercebida.

Fundamentação teórica · 2

Autorização em três dimensões

Verificar se um usuário está autenticado responde apenas à primeira dimensão da autorização. Uma política completa exige três perguntas independentes para cada operação: Sujeito (quem age), Objeto (qual recurso específico) e Ação/Condição (o que pode ser feito e em qual estado).

01

As três dimensões

  • Sujeito: quem age? Qual é o papel e o contexto do usuário autenticado?
  • Objeto: sobre o quê? Qual recurso específico está sendo acessado?
  • Ação/Condição: o que pode ser realizado e em qual estado o sistema permite isso?
02

Acesso horizontal e vertical

03

Condição insegura

O código abaixo localiza o pedido e retorna o recurso sem verificar a quem ele pertence. Passe o mouse sobre as palavras sublinhadas para entender cada parte:

const order = orders.find(o => o.id === Number(req.params.id)); return res.json(order); // sem verificar order.ownerId
04

O que a correção deve garantir

Localizar o recurso pelo ID não é suficiente. Antes de retornar ou modificar, o código deve confirmar que o pedido pertence ao usuário autenticado e à mesma organização:

// Verificação de propriedade if (!order || order.ownerId !== currentUser.id) { return res.status(403).json({ error: 'Forbidden' }); } // Verificação de organização if (order.orgId !== currentUser.orgId) { return res.status(403).json({ error: 'Forbidden' }); } return res.json({ id: order.id, status: order.status });

A resposta final expõe apenas os campos necessários para a operação, não o objeto completo.

CWE-639

Authorization Bypass Through User-Controlled Key

Vulnerabilidade em que a autorização é contornada porque a chave de acesso ao recurso (como um ID de pedido) é controlada pelo próprio usuário. O sistema verifica autenticação mas não valida que o recurso identificado pertence ao solicitante.

Exemplo: um comprador substitui o ID do seu pedido pelo de outro usuário na URL e obtém acesso ao recurso alheio. A autenticação ocorre corretamente, mas a verificação do objeto falha.

Fundamentação teórica · 3

Regras de negócio e estados de um pedido

Uma funcionalidade pode executar corretamente uma operação e, ainda assim, violar as regras de segurança do sistema. Imagine uma API para gerenciar pedidos: cada pedido possui um estado, e a ação de aprovação deve respeitar regras sobre quem pode aprovar e em quais condições isso é permitido.

01

O cenário: aprovação de um pedido

Um pedido foi criado e está com status pending. Quando um usuário solicita sua aprovação, a aplicação recebe a requisição e precisa decidir se a operação pode ser realizada.

Não basta que o endpoint exista e receba um status válido. A aplicação precisa verificar as condições de negócio antes de modificar o pedido.

02

Quais regras precisam ser respeitadas?

A aprovação depende de três verificações:

  • Estado: o pedido precisa estar pending para passar a approved.
  • Autorização: o usuário deve possuir permissão para aprovar aquele pedido.
  • Rastreabilidade: a operação deve registrar quem aprovou, qual pedido foi alterado e quando.
03

Onde surge a vulnerabilidade?

Imagine que o endpoint simplesmente localize o pedido e altere seu status para approved, sem consultar seu estado atual ou verificar as permissões do usuário.

Um usuário sem autorização poderia aprovar pedidos, ou um pedido em estado incompatível poderia ser aprovado indevidamente. A aplicação executaria a atualização sem erro técnico, mas o resultado violaria as regras de negócio.

04

O papel da revisão manual

Durante a revisão do código, não basta procurar erros de sintaxe, injeções ou funções inseguras. O revisor precisa compreender como o processo deveria funcionar e verificar se o código implementa as restrições necessárias.

É justamente nesse tipo de análise que a revisão manual orientada por requisitos e regras de negócio se torna importante, especialmente quando essas regras não estão formalizadas para uma ferramenta automatizada.

Estudos sobre revisão de código e segurança, como o de Braz et al., discutem a importância de direcionar a atenção do revisor para aspectos específicos de segurança, em vez de depender apenas de uma inspeção genérica do código. A referência completa encontra-se na seção de Referências deste material.

Checklists são apoio, não substituição de raciocínio

01

Uma lista de checagem evita esquecer classes de falha recorrentes. No entanto, ela deve ser complementada pelo conhecimento da aplicação e do cenário de ameaça.

02

Utilize o OWASP ASVS 5.0.0 para derivar requisitos verificáveis, registrando edição e identificador quando for usado um requisito específico. Não atribuir números de requisitos de memória.

03

Fundamentação teórica · 5

Anatomia de um achado bem documentado

01

Localização: arquivo, função, linha e commit analisado. Sem isso o achado não pode ser reproduzido.

02

Condição: qual perfil, qual entrada e qual estado tornam o problema observável. Um IDOR exige saber com qual token e qual ID testar.

03

Impacto: o que acontece se a condição for satisfeita. Acesso a dados de outro tenant? Aprovação indevida? Qual a consequência de negócio?

04

Classificação: CWE relevante, nível de confiança (confirmado, hipótese, investigar) e indicação de requisito ASVS violado quando aplicável.

05

Recomendação: correção proposta e teste negativo que demonstra a ausência do problema após a correção.

// OrderService: exemplo didático independente da API real
async getOrder(orderId: number, requestingUser: User) {
  const order = await this.orderRepo.findById(orderId);
  if (!order) throw new NotFoundException();
  return order;
}
Mostrar discussão orientadora

O método verifica a existência do pedido, mas não verifica se requestingUser tem relação com ele. Qual informação faltaria para decidir se isso é vulnerabilidade confirmada ou hipótese?

  • Quem chama esse método e com qual contexto de usuário?
  • Existe verificação de organização e propriedade em outro ponto da cadeia?
  • O endpoint que usa esse serviço exige papel específico?

Este exemplo é independente da API avaliada no projeto.
