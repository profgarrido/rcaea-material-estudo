Estar autenticado significa estar autorizado?

Referência histórica · First American Financial, 2019

Um problema de controle de acesso no sistema de documentos da First American Financial permitia acesso a documentos por URLs com identificadores previsíveis. A situação foi objeto de procedimentos da autoridade financeira de Nova York (NYDFS).

Atenção: exposição potencial não equivale a confirmação de que todos os documentos foram efetivamente acessados.

Você recebeu um link legítimo para consultar um documento. Ao modificar um número da URL, consegue visualizar um documento de outra pessoa.

O problema está no usuário que alterou o endereço, ou na aplicação que permitiu o acesso?

O que faltou verificar na API?

O sistema conhece Ana (autenticação), mas não verifica se Ana tem relação com o documento 1002 ou 1003 (autorização). A API deveria checar: este usuário pode acessar este recurso específico?, não apenas se está autenticado.

Autenticação no middleware não substitui autorização contextual. O service é o lugar típico para coordenar a regra de negócio; o repository pode reforçar com consultas corretamente restritas ao escopo autorizado.

Uma aplicação não é segura apenas porque sabe quem você é. Ela também precisa verificar o que você pode fazer. A partir daqui: revisão manual estruturada, IDOR/BOLA, fronteiras de confiança e regras de negócio.

Fundamentação teórica · 1

Revisar código significa reconstruir sua intenção

01

O revisor de segurança procura compreender como dados, privilégios e estados atravessam componentes. A leitura começa no contexto da funcionalidade: requisitos, ativos, perfis de usuários e decisões de acesso.

02

Em seguida identifica pontos de entrada, chamadas críticas e saídas observáveis. Uma implementação não pode ser considerada segura apenas por compilar, passar em testes funcionais ou retornar o HTTP esperado.

03

A OWASP recomenda que o escopo da revisão manual inclua arquitetura, autenticação, autorização, tratamento de erros, lógica de negócio e fluxo de dados.

04

Baseline review: avalia a aplicação de modo abrangente; serve para onboarding, auditoria e conhecimento de legado. Diff-based review: concentra-se nas linhas alteradas e na repercussão sobre controles existentes.

05

Em um Pull Request, o risco pode estar em uma função modificada ou no contrato de uma função que não foi alterada. Revisar apenas o diff verde sem conhecer suas chamadas pode deixar uma vulnerabilidade passar.

Fundamentação teórica · 2

Autorização em três dimensões

01

Analisar apenas if (user) é insuficiente. Para cada operação, perguntar: sujeito (quem age?), objeto (sobre o quê?) e ação/condição (o que pode realizar e em qual estado?).

02

Um endpoint pode negar acesso anônimo e ainda permitir acesso horizontal a outro titular ou acesso vertical a uma função administrativa. A CWE-639 descreve autorização contornável pelo uso de uma chave controlada pelo usuário.

03

Condição insegura ilustrativa: const order = orders.find(o => o.id === Number(req.params.id)); return res.json(order);: retorna o pedido sem verificar a quem pertence.

04

Uma correção exige verificar order.ownerId === currentUser.id e ainda que ambos pertençam à mesma organização. O código correto depende da política de segurança explicitada nos requisitos.

Fundamentação teórica · 3

Regras de negócio e estados de um pedido

01

Considere o endpoint de aprovação de pedido. Não basta ter uma rota POST e um status approved válido. Deve existir um conjunto de transições possíveis: apenas pending → approved, apenas por um aprovador autorizado, com trilha de auditoria.

02

Uma rota que aprova qualquer pedido sem consultar a identidade e o estado permite alteração indevida mesmo sem injeção ou erro sintático.

03

A revisão manual tem vantagem quando o controle depende de política de domínio que não está codificada em anotações ou regras externas.

04

O estudo de Braz et al. sugere que a atenção dirigida à segurança durante a revisão influencia a detecção, reforçando a necessidade de perguntas específicas em vez de listas genéricas.

Fundamentação teórica · 4

Checklists são apoio, não substituição de raciocínio

01

Uma lista de checagem evita esquecer classes de falha recorrentes. No entanto, ela deve ser complementada pelo conhecimento da aplicação e do cenário de ameaça.

02

Utilize o OWASP ASVS 5.0.0 para derivar requisitos verificáveis, registrando edição e identificador quando for usado um requisito específico. Não atribuir números de requisitos de memória.

03

O OWASP Top 10:2025 serve para contextualizar categorias de riscos, não para afirmar que a aplicação passou por verificação integral.

Fundamentação teórica · 5

Anatomia de um achado bem documentado

01

Localização: arquivo, função, linha e commit analisado. Sem isso o achado não pode ser reproduzido.

02

Condição: qual perfil, qual entrada e qual estado tornam o problema observável. Um IDOR exige saber com qual token e qual ID testar.

03

Impacto: o que acontece se a condição for satisfeita. Acesso a dados de outro tenant? Aprovação indevida? Qual a consequência de negócio?

04

Classificação: CWE relevante, nível de confiança (confirmado, hipótese, investigar) e indicação de requisito ASVS violado quando aplicável.

05

Recomendação: correção proposta e teste negativo que demonstra a ausência do problema após a correção.

Exemplo isolado: consulta de pedido

Leia o trecho, formule uma hipótese e só então abra a análise comentada.

// OrderService: exemplo didático independente da API real
async getOrder(orderId: number, requestingUser: User) {
  const order = await this.orderRepo.findById(orderId);
  if (!order) throw new NotFoundException();
  return order;
}
Mostrar discussão orientadora

O método verifica a existência do pedido, mas não verifica se requestingUser tem relação com ele. Qual informação faltaria para decidir se isso é vulnerabilidade confirmada ou hipótese?

  • Quem chama esse método e com qual contexto de usuário?
  • Existe verificação de organização e propriedade em outro ponto da cadeia?
  • O endpoint que usa esse serviço exige papel específico?

Este exemplo é independente da API avaliada no projeto.

Etapa 2 · Revisão manual independente

Use o roteiro abaixo para preparar a prática. Inspecione o código no repositório da equipe e consulte o Moodle para os critérios e a entrega oficial.

  • Percorrer cada rota listada no inventário seguindo o fluxo Route → Controller → Service → Repository.
  • Verificar autorização por objeto em cada endpoint que recebe um ID de recurso como parâmetro.
  • Registrar hipóteses com localização, condição e impacto antes de classificar como confirmado ou pendente.
  • Não consultar resultados de SAST ou IA nesta etapa; preservar a independência da revisão manual.
  • Realizar revisão cruzada com outra equipe usando o modelo de registro acordado.
