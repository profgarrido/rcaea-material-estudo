Para começar, uma pergunta

Uma aplicação pode funcionar corretamente e, ainda assim, ser insegura?

Warm-up · 10 minutos

O sistema funciona. Mas ele é seguro?

Referência histórica · MOVEit Transfer, 2023

Em 2023, uma vulnerabilidade de SQL Injection no MOVEit Transfer (CVE-2023-34362) foi explorada em larga escala. O software de transferência de arquivos funcionava normalmente para seus usuários.

NIST/NVD · CVE-2023-34362

Imagine que um sistema passou em todos os testes funcionais, autentica seus usuários e permite consultar informações corretamente. A equipe considera a funcionalidade concluída.

O que esses testes realmente demonstram sobre a segurança da aplicação?

Votação

Se uma aplicação passa em todos os testes funcionais, podemos considerá-la segura?

Testes funcionais verificam comportamentos esperados nos cenários cobertos. Uma vulnerabilidade pode existir em entradas inesperadas, permissões inadequadas ou caminhos que esses testes não exercitaram. Segurança exige investigação de outros cenários e evidências.

Identifique a decisão perigosa

As duas implementações podem retornar o mesmo resultado para uma entrada válida.

Qual delas apresenta um risco de segurança mais evidente?

Implementação A
const sql =
  `SELECT * FROM users
   WHERE email = '${email}'`;

await prisma.$queryRawUnsafe(sql);

Entrada do usuário interpolada diretamente no texto SQL.

Implementação B
const users =
  await prisma.$queryRaw`
    SELECT * FROM users
    WHERE email = ${email}
  `;

Template tagged do Prisma: valor parametrizado, separado da estrutura SQL.

A é a implementação perigosa. A interpolação direta no texto SQL permite que uma entrada controlada externamente altere a estrutura da consulta (SQL Injection). Em B, o template tagged do Prisma parametriza o valor, preservando a separação entre dado e comando. Não confundir com interpolação arbitrária de identificadores SQL.

Fluxo · Da entrada ao impacto

Uma vulnerabilidade não depende de intenção maliciosa na entrada. Depende do que o código faz com ela.

Entrada não confiável Dado controlado externamente, via HTTP, URL ou cabeçalho ▸

Qualquer dado que chega de fora é entrada não confiável: parâmetros de URL, corpo de requisições POST, cabeçalhos HTTP, cookies, respostas de APIs externas. O problema não está no dado: está no que o código fará com ele.

GET /buscar?q='; DROP TABLE usuarios-- User-Agent: <script>alert(1)</script> Cookie: sessao=../../../etc/passwd

Regra prática: se o valor veio de fora do processo, considere-o não confiável.

↓
Código da aplicação Processa, transforma ou encaminha o dado ▸

O código recebe a entrada e a transforma: concatena strings, monta URLs, insere em templates. É aqui que a separação entre dado e instrução pode ser quebrada.

// Entrada concatenada diretamente na query const sql = "SELECT * FROM users WHERE nome = '" + req.query.nome + "'"; // Entrada inserida diretamente no HTML res.send("<p>Olá, " + req.query.nome + "</p>");

A vulnerabilidade nasce aqui: não na entrada, não no banco.

↓
Operação sensível SQL, comando de sistema, chamada de API, renderização HTML ▸

Operações sensíveis são pontos onde dados se tornam ações, chamados de sinks. O sink em si não é o problema: o problema é a chegada de entrada não confiável sem validação.

SinkRisco
db.query(sql)Injeção de SQL
exec(cmd)Injeção de comando
innerHTML = valXSS
eval(code)Execução arbitrária
fs.readFile(path)Path traversal

Encontrar um sink em auditoria é o início da investigação, não a confirmação da vulnerabilidade.

↓
Possível impacto Clique para revelar após a discussão ▸

O impacto depende do sink atingido e do contexto da aplicação.

VulnerabilidadeImpacto possível
SQL InjectionDados de todos os usuários, bypass de login, deleção de tabelas
XSS StoredRoubo de sessão, redirecionamento malicioso
Command InjectionAcesso ao sistema operacional, instalação de malware
Path TraversalLeitura de arquivos fora do escopo, exposição de segredos

A revisão de código busca identificar o caminho antes que o impacto se concretize.

Código funcional não é sinônimo de código seguro. A segurança exige compreender como o software se comporta quando recebe entradas, solicitações e interações que não fazem parte do fluxo esperado. A partir daqui: vulnerabilidade, ameaça, risco, OWASP Top 10 e revisão de código.

Tipos de revisão de código

  • Funcional: verifica se o código faz o que foi pedido
  • Qualidade: verifica legibilidade, manutenibilidade e cobertura de testes
  • Segurança: verifica se o código pode ser explorado por quem não deveria ter acesso
  • As três perspectivas são complementares: código correto e limpo ainda pode ser inseguro
Exemplo Endpoint de login: funcional verifica se o usuário entra; qualidade verifica clareza do código; segurança verifica se a comparação de senha usa tempo constante, se há rate limiting e se o erro não revela qual campo falhou.

Vocabulário de segurança

  • Ativo: o que tem valor: dados, sessões, credenciais
  • Ameaça: quem ou o que pode causar dano
  • Fraqueza (CWE): falha no código ou no design do sistema
  • Vulnerabilidade: fraqueza explorável em um contexto específico
  • Risco: combinação de probabilidade e impacto
Exemplo Ativo: registros de usuários. Ameaça: atacante externo. Fraqueza: CWE-89. Vulnerabilidade: endpoint /buscar sem parametrização. Risco: alto.

Autenticação vs. Autorização

  • Autenticação: responde "quem é você?" e verifica identidade
  • Autorização: responde "o que você pode fazer?" e verifica permissões
  • São camadas independentes: passar pela autenticação não garante autorização
  • Falhas em cada camada têm causas e controles diferentes
Exemplo Usuário autenticado que acessa /admin/relatorio sem checar se é administrador: falha de autorização, não de autenticação. Token válido reutilizado após logout: falha de autenticação.

O padrão de injeção

  • Ocorre quando dados externos são interpretados como parte de um comando ou consulta
  • Não é exclusivo de SQL: aparece em comandos de sistema, templates e renderização HTML
  • A fraqueza está no código que mistura dado e instrução
  • A entrada em si não é o problema: é o que o código faz com ela
Exemplos SQL: "SELECT … WHERE id = " + req.params.id
Comando: exec("ls " + userInput)
XSS: innerHTML = userInput com payload <script>…</script>

Taxonomias e referências

  • OWASP Top 10: categorias de risco mais prevalentes em aplicações web
  • CWE: catálogo de fraquezas no código (causas raiz)
  • CVE: instâncias de vulnerabilidades em software específico
  • CVSS: sistema de pontuação de severidade (0 a 10)
  • ASVS: padrão de verificação para auditorias de segurança
Exemplo SQL Injection: A03:2021 no OWASP Top 10, CWE-89 como causa, registrada como CVE com CVSS 9.8, verificável pelo item 5.3.4 do ASVS.

Hipóteses rastreáveis

  • Código: onde está a potencial fraqueza (arquivo, linha, parâmetro)
  • Condição: como poderia ser explorada por um atacante
  • Impacto: o que aconteceria se fosse explorada com sucesso
  • Não afirma exploração: afirma possibilidade verificável e rastreável
Exemplo "O parâmetro id (linha 42, UserController.java) é concatenado na query SQL (linha 47). Se um atacante enviar 1 OR 1=1, a cláusula WHERE é contornada, expondo todos os registros."

Fundamentação teórica · 1

Segurança como propriedade do software, não apenas da infraestrutura

01

Um sistema pode ter HTTPS, firewall, autenticação e logs e ainda expor dados por uma falha no controle de autorização de um endpoint. Segurança no código exige examinar quais ações são permitidas, para quem, sobre quais recursos e sob quais condições.

02

A análise não é sinônimo de encontrar sintaxe ruim. Parte dos riscos está na relação entre a implementação e os requisitos de negócio que definem quem pode fazer o quê.

03

McGraw posiciona práticas de segurança em todo o ciclo de desenvolvimento. O NIST SSDF orienta a prevenção e a mitigação de vulnerabilidades ao longo desse ciclo, não apenas ao final.

04

Revisão de código identifica problemas antes da entrega. Testes exercitam caminhos executáveis. Análise estática oferece escala sobre padrões conhecidos. Modelagem de ameaças pergunta o que pode dar errado no design. Nenhuma dessas práticas substitui completamente as outras.

05

O NIST IR 8397 recomenda técnicas múltiplas de verificação, entre elas análise estática, detecção de segredos e testes. A combinação delas é o tema central desta disciplina.

Fundamentação teórica · 2

Revisão funcional, de qualidade e revisão de segurança

01

Revisão funcional verifica se a alteração atende à história ou ao requisito. Revisão de qualidade considera clareza, manutenção, tratamento de erros e convenções.

02

Revisão de segurança pergunta se uma entrada maliciosa, um usuário com privilégios insuficientes ou uma mudança inesperada de estado pode causar acesso, processamento ou divulgação indevida.

03

A OWASP diferencia revisão orientada à segurança de uma inspeção geral de código e recomenda analisar lógica, fluxo de dados e controles sensíveis.

04

Exemplo concreto: um método getOrder(id) pode ser correto funcionalmente, ter tipos adequados e retornar status HTTP consistente. Mesmo assim, se um usuário autenticado receber um pedido que pertence a outro, há uma fraqueza de autorização. O erro não aparece em linters ou verificações de tipo.

Fundamentação teórica · 3

Do risco ao achado: ativo, ameaça, fraqueza e impacto

01

Quatro perguntas estruturam qualquer revisão:

  • O que protegemos? (dados de pedidos, tokens, informações pessoais)
  • Quem interage? (usuário, serviço, administrador)
  • Por onde os dados entram? (parâmetro de rota, body, header, fila, variável de ambiente)
  • Qual controle deveria mediar a ação? (validação, autenticação, autorização, parametrização)
02

Uma suspeita se torna achado defendido quando está associada a um trecho de código, uma condição de exploração e um efeito concreto. Padrão suspeito não é vulnerabilidade confirmada.

03

Terminologia essencial:

  • CWE cataloga classes de fraquezas de software
  • CVE identifica vulnerabilidades divulgadas em produtos específicos
  • CVSS descreve características e severidade de vulnerabilidades avaliadas
04

OWASP Top 10 não é checklist completo de testes, mas documento de conscientização. A versão 2025 coloca controle de acesso quebrado em A01, injeção em A05 e falhas de autenticação em A07. Para critérios verificáveis, use o OWASP ASVS 5.0.0.

Fundamentação teórica · 4

Autenticação não é autorização

Autenticação

Quem é o sujeito?

Confirma a identidade. Um token válido garante que sabemos de quem se trata, mas não o que esse sujeito pode fazer.

  • JWT assinado e verificado
  • Sessão ativa no servidor
  • Resultado: identidade confirmada
Autorização

O que esse sujeito pode fazer?

Decide permissões sobre cada recurso específico. Depende de papel, organização, propriedade e estado.

  • Papel (CUSTOMER, APPROVER, MANAGER)
  • Organização do sujeito vs. do recurso
  • Propriedade do objeto (order.ownerId)
01

Em APIs com identificadores na URL, verificar somente a existência do objeto não basta. É preciso relacioná-lo ao sujeito, seu papel e, eventualmente, à organização a que pertence. A MITRE documenta em CWE-639 o desvio de autorização por chave controlada pelo usuário.

02

No laboratório, o login emite um JWT verificado criptograficamente. O servidor obtém a identidade do usuário validado. Isso não resolve, por si só, as decisões de autorização de cada pedido. Avalie papel, organização, propriedade e estado separadamente.

Fundamentação teórica · 5

Injeção: quando dados passam a ser interpretados como instruções

01

Uma falha de injeção ocorre quando dados não confiáveis alcançam um interpretador sem delimitação adequada entre conteúdo e comando. SQL construído por concatenação e execução de comando de sistema com texto controlado externamente são exemplos típicos.

02

A correção preferencial é usar mecanismos estruturados e parametrizados, além de reduzir privilégios. Validação de entrada é defesa adicional, não substitui parametrização.

03

Atenção: um padrão de construção insegura não prova, por si só, um ataque bem-sucedido. É preciso verificar se a string efetivamente chega ao banco sem parametrização e de onde ela vem.

04

A análise estática pode sinalizar esse padrão com uma regra de taint; a revisão manual verifica se existe um fluxo real entre o dado externo e a chamada não parametrizada.

Conceito em perspectiva

SQL: dado ou comando? Interpolação versus parametrização

CÓDIGO COMENTADO

O que muda entre as duas abordagens

Construção suspeita: interpolação
// dado externo compõe o texto da instrução
function findUser(username: string) {
  const sql = `SELECT id FROM users
    WHERE username = '${username}'`;
  return db.query(sql);
}

O valor de username torna-se parte da instrução SQL. Se vier de entrada HTTP sem sanitização, abre espaço para injeção.

Consulta parametrizada (recomendada)
// instrução e valor trafegam separadamente
function findUser(username: string) {
  const sql = 'SELECT id FROM users WHERE username = $1';
  const params = [username];
  return db.query(sql, params);
}

O driver recebe instrução e valor separados. O interpretador não pode confundir dado com comando.

O que verificar na revisão

Encontrar o padrão de interpolação não prova exploração. Rastreie: de onde vem o valor? Passa por alguma sanitização antes? Existe outro mecanismo que parametrize a chamada?

Fundamentação teórica · 6

O que a revisão manual vê que uma ferramenta pode perder

01

A revisão manual relaciona regras de negócio, estados, papéis e intenções de design. Uma ferramenta reconhece operações perigosas e fluxos configurados, mas não compreende automaticamente toda política organizacional.

02

O estudo de Braz e Bacchelli identifica dificuldades de desenvolvedores para avaliar segurança em revisões e reforça a necessidade de treinamento específico. Isso motiva a dinâmica desta disciplina: primeiro o olhar humano, depois o alerta automatizado.

03

Por outro lado, ferramentas cobrem escala e consistência: varrem todo o repositório sem fadiga, seguem regras declaradas e produzem resultados repetíveis em diferentes versões do código. A revisão humana não tem a mesma escala.

04

A conclusão prática é que nem ausência de alerta confirma ausência de vulnerabilidade, nem presença de alerta confirma vulnerabilidade explorável. Ambas as abordagens precisam de julgamento contextual.

Conceito em perspectiva

Revisão manual e SAST: o que cada uma cobre

CONTRASTE

Pontos fortes e lacunas das duas abordagens

Dimensão Revisão manual SAST / Semgrep / CodeQL
Regras de negócio Consegue relacionar política, estado e intenção de design Não interpreta política organizacional não codificada
Escala Limitada pela capacidade e atenção humana Varre repositório completo de forma consistente
Padrões conhecidos Depende do conhecimento do revisor Aplica regras declaradas com precisão e repetibilidade
Fluxo de dados intermodular Requer rastreamento manual entre funções Pode modelar source → sink entre módulos (CodeQL)
Falsos positivos Menor, com contexto adequado Presente; exige triagem por quem entende o contexto

A ausência de alerta não confirma a ausência de vulnerabilidades, e a presença de alerta não confirma exploração. Ambas as abordagens são complementares.

function findUser(email: string) {

Mostrar discussão orientadora

Perguntas que orientam a análise:

  • Qual é a origem de email? Vem de uma requisição HTTP, de um arquivo de configuração ou de outro lugar?
  • A consulta enviada ao banco é parametrizada ou contém texto interpolado?

O padrão de interpolação é suspeito, mas a confirmação exige rastrear o fluxo do dado. Não confunda padrão suspeito com exploração demonstrada.

  • Mapear as rotas disponíveis e relacioná-las a quais recursos expõem e quais papéis deveriam acessá-las.
  • Produzir três hipóteses fundamentadas e preservar a referência do commit inicial. Não corrigir nem usar SAST ou IA nesta etapa.
