Você concorda com a IA?

Resposta fictícia de assistente de IA

"O código não possui vulnerabilidade porque os dados são utilizados apenas para gerar logs."

Essa conclusão é tecnicamente suficiente?

A conclusão é insuficiente. É preciso investigar: biblioteca utilizada, versão, configuração, caminho do processamento, comportamento do componente e condições reais de exploração. A resposta de IA é uma hipótese a validar, não prova de segurança.
Evidências necessárias: (1) qual biblioteca de logging é usada; (2) qual versão está em uso; (3) a versão possui vulnerabilidade conhecida neste mecanismo; (4) o valor chega sem sanitização ao componente vulnerável; (5) o ambiente de execução aplica as condições de exploração.

Uma entrada não é segura apenas porque parece inofensiva. É preciso compreender o caminho percorrido pelos dados e o comportamento das operações que os recebem. A partir daqui: source, sink, propagação, sanitização, CodeQL e limitações da IA.

Fundamentação teórica · 1

Da AST ao comportamento possível: três representações

01

AST (Abstract Syntax Tree): representa construções do código como chamadas, expressões e declarações. Útil para procurar a forma de um programa.

02

CFG (Control Flow Graph): descreve caminhos possíveis de execução, sujeitos a condições e desvios. Uma condição typeof x === 'string' comprova tipo, mas não torna um dado seguro.

03

Grafo de fluxo de dados: descreve relações entre origens e usos de valores. Permite rastrear como um dado externo chega a uma operação sensível através de chamadas e atribuições.

04

O CodeQL fornece bibliotecas para análise de fluxo de dados em JavaScript/TypeScript, distinguindo nós AST de nós de fluxo. Combinações das três representações aumentam a cobertura, mas nenhuma elimina todos os falsos negativos.

Fundamentação teórica · 2

Sources, sinks, propagadores e barreiras na prática

01

Source: ponto de entrada de dados potencialmente não confiáveis. Parâmetro HTTP, arquivo enviado pelo usuário ou mensagem de fila externa são exemplos.

02

Propagação: operações que transferem influência da entrada para outros valores: atribuição, concatenação, parâmetros e retornos de função.

03

Sink: operação em que controlar o argumento pode causar efeito de segurança: consulta não parametrizada, execução de shell, montagem de HTML, leitura de caminhos sensíveis.

04

Sanitizer / barreira: transformação ou checagem adequada ao contexto da sink que impede o fluxo inseguro. A validação de tipo (typeof x === 'string') geralmente não é sanitização de comando.

// Exemplo: source → propagação → sink sem barreira
function handle(req: { query: { filename?: string } }) {
  const filename = req.query.filename;   // source: req.query
  if (typeof filename === 'string') {    // verifica tipo, não sanitiza
    exec(filename);                      // sink: exec com dado externo
  }
}
// A checagem de tipo confirma que é string, mas não impede
// que conteúdo malicioso chegue ao shell.

Fundamentação teórica · 3

CodeQL: modelagem de fluxo e limitações práticas

01

O CodeQL representa o código como banco de dados de fatos e permite consultas em QL. Suporta análise local (dentro de uma função) e global (entre módulos), rastreando propagação de taint.

02

O acesso a funcionalidades avançadas em repositórios privados requer licença institucional. Para o laboratório, trabalhar com resultados fornecidos pelo curso ou com repositório público de demonstração controlado.

03

Mesmo com modelagem de fluxo global, o CodeQL não interpreta política organizacional. Ele pode rastrear que um ID vem de req.params, mas não decide se o sujeito autenticado tem ou não autorização sobre aquele recurso.

04

Resultados de CodeQL precisam de triagem: um caminho source → sink pode ser bloqueado por sanitização não modelada nas bibliotecas utilizadas. Registrar a versão das queries e das extensões de modelo.

Fundamentação teórica · 4

Revisão assistida por IA: hipótese, não diagnóstico

01

A IA generativa pode apoiar: explicação de código, elaboração de checklists, hipóteses de risco, identificação de testes negativos e proposição de correções.

02

Hipóteses de IA precisam ser validadas contra evidências concretas: localização no código, condição reproduzível e impacto verificado. Uma resposta sem essas três informações é ponto de partida, não conclusão.

03

Nas entregas: registrar ferramenta/modelo, propósito da consulta, informações fornecidas e resultado da validação independente. Nunca encaminhar credenciais, tokens, arquivos .env ou dados reais para ferramentas externas.

04

Comparar as hipóteses de IA com os achados manuais (aula 2) e os alertas SAST (aula 3) para identificar convergência e divergência. Divergência pode indicar falso positivo da IA, falso negativo da ferramenta, ou nova hipótese a investigar.

Fundamentação teórica · 5

Por que falhas de autorização resistem à análise de taint

01

Em GET /orders/:id, o código busca por chave e responde ao cliente. Uma ferramenta poderia saber que um usuário A não deve consultar o pedido de B? Somente se a política for modelada com dados, anotações ou regras apropriadas.

02

Um grafo de taint pode descobrir que a chave vem da URL. Entretanto, conhecer a origem da chave não define quem pode acessar o registro. O método manual da aula 2 continua necessário para entender proprietários e privilégios.

Mostrar discussão orientadora

Source: req.query.file: parâmetro HTTP controlável pelo cliente.
Propagação: const input = req.query.file: atribuição transfere a influência.
Sem barreira adequada: typeof input === 'string' verifica tipo, não sanitiza.
Sink: exec(input): execução de shell com dado externo.
