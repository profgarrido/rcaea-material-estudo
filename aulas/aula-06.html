Qual conclusão o relatório suporta?

Selecione a afirmação mais adequada para encerrar um relatório de auditoria.

Uma auditoria não termina quando alguém diz que corrigiu um problema. Ela termina quando existe uma conclusão sustentada pelas evidências disponíveis e pelos limites da verificação. A partir daqui: validação, testes de regressão, riscos residuais e comunicação técnica.

Fundamentação teórica · 1

A auditoria responde a uma pergunta delimitada

01

A pergunta desta disciplina: quais vulnerabilidades e padrões de risco foram identificados por revisão manual e por análise automatizada na aplicação de estudo, e o que cada técnica deixou de identificar na configuração utilizada?

02

"O código é seguro" é uma afirmação muito mais forte do que "não encontramos novos alertas sob estas regras e nesta versão". A segunda é uma conclusão honesta e técnica; a primeira geralmente não.

03

Escopo mínimo a declarar: commit identificado, rotas analisadas, arquivos cobertos, regras e versões das ferramentas, requisitos de autorização examinados, critérios de classificação e limitações explícitas.

04

O NIST SSDF recomenda práticas integradas de prevenção, verificação e tratamento. A OWASP destaca lacunas que exigem entendimento humano. Nenhum framework substitui o escopo explícito da auditoria.

Fundamentação teórica · 2

Correção exige validação independente

01

Modificar o código não equivale automaticamente a remover o risco. Uma correção precisa ser validada por testes que reproduzam a condição original e demonstrem o comportamento corrigido.

02

Testes negativos verificam que o acesso indevido é negado. Testes positivos verificam que o acesso legítimo ainda funciona. Ambos são necessários: corrigir um IDOR sem quebrar o fluxo autorizado.

03

Após a correção, reexecutar as verificações usadas nas etapas anteriores (Semgrep, CodeQL se disponível) para confirmar que o padrão detectado foi eliminado ou deixou de ser alcançável.

04

Risco residual deve ser declarado: o que ainda não foi coberto pela análise, o que foi deliberadamente não corrigido e por quê, e quais controles compensatórios existem.

Conceito em perspectiva

Validar uma correção exige os dois lados

CÓDIGO COMENTADO

Teste negativo e teste positivo para o mesmo controle

Teste negativo (acesso indevido)
it('deve negar acesso a pedido de outro tenant', async () => {
  const response = await request(app)
    .get('/orders/200')
    .set('Authorization', `Bearer ${tokenOfAlice}`);
  expect(response.status).toBe(403);
});

Verifica que o acesso indevido é bloqueado.

Teste positivo (acesso legítimo)
it('deve retornar pedido do próprio tenant', async () => {
  const response = await request(app)
    .get('/orders/100')
    .set('Authorization', `Bearer ${tokenOfAlice}`);
  expect(response.status).toBe(200);
});

Verifica que o acesso legítimo ainda funciona.

Exemplos independentes da API avaliada no projeto. Uma correção que bloqueia tudo (incluindo o acesso legítimo) não é uma correção adequada.

Fundamentação teórica · 4

Reprodutibilidade e validade do laboratório

01

Dois grupos podem obter números diferentes porque analisaram commits distintos, instalaram versões diferentes, utilizaram configurações diferentes ou selecionaram áreas diferentes do projeto.

02

Para comparar resultados, registrar: artefato, ambiente, ferramenta/versão, configuração, data, unidade do achado e método de validação.

03

Nosso laboratório é propositalmente pequeno, com vulnerabilidades inseridas e sem amostragem representativa. Há validade pedagógica, não generalização científica sobre performance de ferramentas no mercado.

04

A pesquisa de Braz et al. sobre revisão com foco explícito em segurança ajuda a justificar a comparação de técnicas humanas e automatizadas, mas não permite concluir que uma técnica é universalmente superior.

Exemplo isolado: teste negativo

Leia o trecho, formule uma hipótese e só então abra a análise comentada.

it('deve negar acesso a fatura de outro usuário', async () => {
  const response = await request(app)
    .get('/invoices/200')
    .set('Authorization', `Bearer ${tokenOfAlice}`);
  expect(response.status).toBe(403);
});
Mostrar discussão orientadora

Um teste negativo deve ser acompanhado de teste positivo para garantir que o acesso legítimo permaneça possível. O que mais seria necessário verificar?

  • O teste usa um token real de Alice ou um mock?
  • O ID 200 pertence realmente a outro usuário no ambiente de teste?
  • Existe um teste correspondente que verifica que Alice acessa suas próprias faturas com 200?

Este exemplo é independente da API avaliada no projeto.

Etapa 6 · Auditoria e entrega final

Use o roteiro abaixo para preparar a prática. Inspecione o código no repositório da equipe e consulte o Moodle para os critérios e a entrega oficial.

  • Congelar o estado anterior às correções e selecionar os riscos prioritários com base na matriz da etapa 5.
  • Corrigir vulnerabilidades selecionadas preservando o contrato da API e os testes funcionais existentes.
  • Escrever testes negativos e positivos para cada correção realizada.
  • Reexecutar verificações aplicáveis; registrar resultados antes e depois das correções e declarar riscos residuais.
  • Consolidar relatório técnico e repositório; preparar síntese de dois minutos por equipe e entregar no Moodle.
