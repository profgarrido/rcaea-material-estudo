A ferramenta encontrou uma vulnerabilidade. Será?

Referência real · Análise estática no Google, 2018

Quando uma ferramenta encontra muitos problemas, isso significa que ela está fazendo um bom trabalho?

Imagine uma empresa como o Google, com milhares de desenvolvedores modificando continuamente o código de diferentes sistemas. Para identificar problemas antes que essas alterações fossem incorporadas aos produtos, a empresa passou a integrar ferramentas de análise estática ao processo de desenvolvimento e revisão de código.

Mas surgiu um desafio: encontrar um problema automaticamente não significa que o alerta será útil para o desenvolvedor.

Em um estudo publicado em 2018, Sadowski e colaboradores descrevem essa experiência e destacam uma lição importante: ferramentas de análise estática precisam produzir resultados confiáveis, compreensíveis e que ajudem os desenvolvedores a tomar decisões.

A questão não é apenas quantos alertas uma ferramenta encontra, mas o que conseguimos fazer com eles.

Sadowski et al. (2018). Lessons from Building Static Analysis Tools at Google. DOI: 10.1145/3188720

Alertas incorretos, pouco relevantes ou difíceis de compreender podem consumir tempo, dificultar a priorização e diminuir a confiança nas ferramentas.

Fundamentação teórica · 1

Como uma ferramenta analisa o código sem executar a aplicação?

Imagine que sua equipe desenvolveu uma API com dezenas de endpoints.

Para investigar possíveis vulnerabilidades, vocês poderiam iniciar o servidor, autenticar usuários e executar requisições HTTP.

Mas também existe outra possibilidade: examinar diretamente o código da aplicação, antes mesmo de colocar seus endpoints em execução.

Essa é a ideia central da análise estática.

01 O que é

O que significa analisar o código estaticamente?

A análise estática examina o programa sem executar seus fluxos operacionais.

Em vez de enviar requisições para descobrir como a aplicação responde, uma ferramenta pode inspecionar arquivos TypeScript, identificar chamadas de funções, verificar padrões e analisar determinadas relações entre os dados.

Quando esse processo é direcionado à identificação de problemas de segurança, utilizamos o termo SASTStatic Application Security Testing. Técnica que analisa código ou outras representações do programa sem executar a aplicação para identificar possíveis problemas de segurança. (Static Application Security Testing).

Exemplo: Uma ferramenta SAST pode procurar consultas SQL construídas de maneira insegura mesmo que a API nunca tenha recebido uma requisição maliciosa.

O SAST investiga como o código foi escrito, não apenas como a aplicação se comporta durante sua execução.

↓
02 Como interpreta

Como a ferramenta compreende o código?

Uma ferramenta não precisa interpretar o código apenas como uma sequência de palavras. Dependendo de sua implementação, ela pode analisar diferentes representações do programa:

  • Texto e tokensUnidade reconhecida durante a análise léxica do código, como uma palavra-chave, um identificador ou um operador.: identificação de elementos presentes no código, como nomes de funções, operadores e palavras-chave.
  • ASTAbstract Syntax Tree, ou Árvore Sintática Abstrata. Representação da estrutura sintática do código, incluindo expressões, chamadas de funções e condições. (Abstract Syntax Tree): árvore sintática abstrata que representa a estrutura do código, permitindo reconhecer chamadas de funções, expressões, condições e outros elementos.
  • Fluxo de dadosRelação que permite acompanhar como informações são recebidas, transformadas e utilizadas em diferentes partes do programa.: análise de como um valor é recebido, transformado e encaminhado entre diferentes operações.

Exemplo com a instrução:

await prisma.$queryRawUnsafe(sql);
Representação estrutural (didática)
Chamada de método
Objeto: prisma
Método: $queryRawUnsafe
Argumento: sql

Representação simplificada para fins didáticos. Não corresponde à AST completa produzida por um parser TypeScript.

Uma ferramenta que compreende a estrutura sintática consegue reconhecer que existe uma chamada ao método $queryRawUnsafe e identificar o argumento utilizado. Dependendo de suas capacidades, ela também pode investigar de onde veio o valor de sql.

Atenção: Nem toda ferramenta realiza todas essas análises. Algumas trabalham principalmente com padrões sintáticos, enquanto outras conseguem acompanhar relações de fluxo de dados mais complexas.

04 Limites

O que a análise estática pode deixar de perceber?

Uma ferramenta consegue identificar muitos problemas associados a padrões conhecidos. Entretanto, determinados riscos dependem de informações que não estão explícitas no código ou que não foram representadas nas regras de análise.

Considere uma API de pedidos. Um endpoint pode atualizar corretamente o status de um pedido, mas permitir que um usuário sem autorização realize essa operação. Se a ferramenta não conhece a política de aprovação da organização, ela pode não identificar a violação dessa regra de negócio.

A ausência de alertas não significa ausência de vulnerabilidades. A análise estática deve ser combinada com revisão manual, testes e outras técnicas de verificação.

Se a análise estática examina o código sem executar a aplicação, como podemos investigar problemas que dependem do comportamento do sistema ou das bibliotecas utilizadas?

É aqui que entram outras técnicas de segurança, como DAST, SCA e Secret Scanning, apresentadas na próxima seção.

Chess, B. e West, J. (2007). Secure Programming with Static Analysis. Addison-Wesley. Discutem como integrar análise estática à revisão de código e por que encontrar defeitos potenciais demanda interpretação. · NIST IR 8397 recomenda varreduras estáticas para localizar classes de problemas, mas não as apresenta como método exclusivo de verificação.

Conceito em perspectiva

Diferentes técnicas, diferentes perspectivas sobre a segurança

A análise estática permite investigar possíveis problemas diretamente no código. Entretanto, nem todos os riscos podem ser identificados dessa maneira.

Outras técnicas analisam o comportamento da aplicação em execução, as dependências utilizadas ou a presença de credenciais expostas.

Cada abordagem responde a perguntas diferentes.

CONTRASTE

Nenhuma técnica oferece uma visão completa da segurança.

Uma aplicação pode não apresentar alertas no SAST e ainda possuir problemas de comportamento, dependências vulneráveis ou regras de negócio inadequadas.

A combinação de técnicas permite investigar diferentes aspectos do software.

Fundamentação teórica · 2

Do texto ao modelo: AST e reconhecimento de padrões

01

Uma regra muito simples procura a ocorrência textual exec(. O problema: exec pode nomear uma função inocente, uma importação diferente ou uma chamada com argumento constante sem entrada externa.

02

Um reconhecedor baseado em AST considera a estrutura sintática de uma chamada, reduzindo parte do ruído, mas por si só não prova que a entrada é controlável por um adversário.

03

Desempenho e precisão variam conforme a regra, a linguagem, o framework e o contexto do projeto. Uma mesma regra pode ter precisão diferente em projetos distintos.

04

Uma regra de padrão exec(...) encontra ambas as chamadas abaixo. O primeiro trecho pode ser vulnerabilidade se input for não confiável; o segundo não demonstra injeção por entrada externa. O alerta é uma proposta de investigação, não um juízo final.

Entrada a investigar
function concerning(input: string) {
  exec(input); // origem a rastrear
}

Fonte de input precisa ser verificada.

Argumento literal
function staticCase() {
  exec('echo lab'); // argumento fixo
}

Pode gerar alerta pelo mesmo padrão; exige leitura contextual.

Fundamentação teórica · 3

Falsos positivos, falsos negativos e precisão

01

Verdadeiro positivo (VP): alerta corresponde a um problema confirmado segundo critério definido.

02

Falso positivo (FP): alerta sinaliza como vulnerabilidade um caso não vulnerável no contexto validado. Marcar FP apenas para "limpar painel" sem justificativa é uma prática problemática.

03

Falso negativo (FN): uma vulnerabilidade presente no código não é sinalizada pela regra. Só pode ser contado se houver referência independente.

04

Exemplo hipotético: uma regra encontra 8 ocorrências, 5 confirmadas; existem 2 vulnerabilidades não detectadas. Precisão = 5/8 (62,5%). Revocação = 5/7 (71,4%). Não estimar esses valores sem um conjunto de referência validado.

Como classificar cada alerta na triagem

MAPA

Quatro categorias possíveis para cada ocorrência

Verdadeiro positivo

Confirmar

Alerta corresponde a problema demonstrável com condição, fluxo e impacto documentados.

Falso positivo

Descartar (justificado)

Padrão presente, mas o dado não chega ao interpretador ou existe sanitização adequada. Exige justificativa.

Necessita investigação

Pendente

Contexto insuficiente para decidir. Registrar o que falta verificar e quem é responsável.

Risco aceito

Documentar

Problema conhecido, correção inviável no momento. Registrar decisão e responsável com data de reavaliação.

Toda decisão de triagem precisa de justificativa registrada e rastreável ao commit analisado.

Fundamentação teórica · 4

Semgrep: estrutura de uma regra

01

Uma regra Semgrep declara: id, languages, severity, message e os operadores de padrão (pattern, pattern-not, pattern-inside, patterns, pattern-either).

02

Metavariáveis como $VAR representam partes variáveis de expressões. $VAR captura qualquer identificador; ... captura argumentos em número variável.

03

A análise de taint do Semgrep permite declarar sources, sinks e sanitizers explicitamente, rastreando o fluxo entre eles sem precisar escrever toda a lógica de propagação.

04

Uma regra útil equilibra sensibilidade (detectar o problema) e precisão (evitar ruído). Regras muito amplas produzem falsos positivos que reduzem a adoção, como evidenciado pelo estudo de Sadowski et al. sobre integração de análise estática no Google.

# Exemplo de estrutura de regra Semgrep (YAML)
rules:
  - id: exec-with-external-input
    languages: [typescript]
    severity: WARNING
    message: Chamada a exec() com argumento possivelmente externo
    patterns:
      - pattern: exec($INPUT)
      - pattern-not: exec("...")   # descarta literais fixos
    metadata:
      cwe: CWE-78

Fundamentação teórica · 5

Critérios para triagem de alertas

01

Para cada ocorrência documentar:

  1. Regra executada
  2. Linha e função
  3. Fonte do argumento
  4. Possibilidade de o caminho ser chamado
  5. Eventual controle sobre o dado
  6. Impacto se o fluxo for alcançado
  7. Nível de confiança
  8. Recomendação
02

Uma ocorrência em código de demonstração não invocado não comprova exploração de uma rota. Pode ainda ser uma má prática e justificar remoção, mas deve ser classificada com precisão.

03

Registrar a versão exata do Semgrep, o conjunto de regras utilizado e o commit analisado. Sem isso, o relatório não pode ser reproduzido.
