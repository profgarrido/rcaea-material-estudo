A ferramenta encontrou uma vulnerabilidade. Será?

Referência real · Análise estática no Google, 2018

Quando uma ferramenta encontra muitos problemas, isso significa que ela está fazendo um bom trabalho?

Imagine uma empresa como o Google, com milhares de desenvolvedores modificando continuamente o código de diferentes sistemas. Para identificar problemas antes que essas alterações fossem incorporadas aos produtos, a empresa passou a integrar ferramentas de análise estática ao processo de desenvolvimento e revisão de código.

Mas surgiu um desafio: encontrar um problema automaticamente não significa que o alerta será útil para o desenvolvedor.

Em um estudo publicado em 2018, Sadowski e colaboradores descrevem essa experiência e destacam uma lição importante: ferramentas de análise estática precisam produzir resultados confiáveis, compreensíveis e que ajudem os desenvolvedores a tomar decisões.

A questão não é apenas quantos alertas uma ferramenta encontra, mas o que conseguimos fazer com eles.

Fundamentação teórica · 1

Como uma ferramenta analisa o código sem executar a aplicação?

Imagine que sua equipe desenvolveu uma API com dezenas de endpoints.

Para investigar possíveis vulnerabilidades, vocês poderiam iniciar o servidor, autenticar usuários e executar requisições HTTP.

Mas também existe outra possibilidade: examinar diretamente o código da aplicação, antes mesmo de colocar seus endpoints em execução.

Essa é a ideia central da análise estática.

01 O que é

O que significa analisar o código estaticamente?

A análise estática examina o programa sem executar seus fluxos operacionais.

Em vez de enviar requisições para descobrir como a aplicação responde, uma ferramenta pode inspecionar arquivos TypeScript, identificar chamadas de funções, verificar padrões e analisar determinadas relações entre os dados.

Quando esse processo é direcionado à identificação de problemas de segurança, utilizamos o termo SASTStatic Application Security Testing. Técnica que analisa código ou outras representações do programa sem executar a aplicação para identificar possíveis problemas de segurança. (Static Application Security Testing).

Exemplo: Uma ferramenta SAST pode procurar consultas SQL construídas de maneira insegura mesmo que a API nunca tenha recebido uma requisição maliciosa.

O SAST investiga como o código foi escrito, não apenas como a aplicação se comporta durante sua execução.

02 Como interpreta

Como a ferramenta compreende o código?

Uma ferramenta não precisa interpretar o código apenas como uma sequência de palavras. Dependendo de sua implementação, ela pode analisar diferentes representações do programa:

  • Texto e tokensUnidade reconhecida durante a análise léxica do código, como uma palavra-chave, um identificador ou um operador.: identificação de elementos presentes no código, como nomes de funções, operadores e palavras-chave.
  • ASTAbstract Syntax Tree, ou Árvore Sintática Abstrata. Representação da estrutura sintática do código, incluindo expressões, chamadas de funções e condições. (Abstract Syntax Tree): árvore sintática abstrata que representa a estrutura do código, permitindo reconhecer chamadas de funções, expressões, condições e outros elementos.
  • Fluxo de dadosRelação que permite acompanhar como informações são recebidas, transformadas e utilizadas em diferentes partes do programa.: análise de como um valor é recebido, transformado e encaminhado entre diferentes operações.

Exemplo com a instrução:

await prisma.$queryRawUnsafe(sql);
Representação estrutural (didática)
Chamada de método
Objeto: prisma
Método: $queryRawUnsafe
Argumento: sql

Representação simplificada para fins didáticos. Não corresponde à AST completa produzida por um parser TypeScript.

Uma ferramenta que compreende a estrutura sintática consegue reconhecer que existe uma chamada ao método $queryRawUnsafe e identificar o argumento utilizado. Dependendo de suas capacidades, ela também pode investigar de onde veio o valor de sql.

Atenção: Nem toda ferramenta realiza todas essas análises. Algumas trabalham principalmente com padrões sintáticos, enquanto outras conseguem acompanhar relações de fluxo de dados mais complexas.

04 Limites

O que a análise estática pode deixar de perceber?

Uma ferramenta consegue identificar muitos problemas associados a padrões conhecidos. Entretanto, determinados riscos dependem de informações que não estão explícitas no código ou que não foram representadas nas regras de análise.

Considere uma API de pedidos. Um endpoint pode atualizar corretamente o status de um pedido, mas permitir que um usuário sem autorização realize essa operação. Se a ferramenta não conhece a política de aprovação da organização, ela pode não identificar a violação dessa regra de negócio.

A ausência de alertas não significa ausência de vulnerabilidades. A análise estática deve ser combinada com revisão manual, testes e outras técnicas de verificação.

Se a análise estática examina o código sem executar a aplicação, como podemos investigar problemas que dependem do comportamento do sistema ou das bibliotecas utilizadas?

É aqui que entram outras técnicas de segurança, como DAST, SCA e Secret Scanning, apresentadas na próxima seção.

Chess, B. e West, J. (2007). Secure Programming with Static Analysis. Addison-Wesley. Discutem como integrar análise estática à revisão de código e por que encontrar defeitos potenciais demanda interpretação. · NIST IR 8397 recomenda varreduras estáticas para localizar classes de problemas, mas não as apresenta como método exclusivo de verificação.

Conceito em perspectiva

Diferentes técnicas, diferentes perspectivas sobre a segurança

A análise estática permite investigar possíveis problemas diretamente no código. Entretanto, nem todos os riscos podem ser identificados dessa maneira.

Outras técnicas analisam o comportamento da aplicação em execução, as dependências utilizadas ou a presença de credenciais expostas.

Cada abordagem responde a perguntas diferentes.

Fundamentação teórica · 2

Por que dois códigos diferentes podem gerar o mesmo alerta?

Uma ferramenta SAST configura regras para detectar padrões no código. Quando uma regra encontra uma correspondência, ela gera um alerta.

Mas o que exatamente a regra está procurando? E por que dois trechos de código muito diferentes podem acionar a mesma regra?

01 O problema

Busca textual versus análise sintática

A forma mais simples de regra procura uma sequência de texto. Por exemplo, procurar a ocorrência literal exec( em qualquer arquivo TypeScript.

O problema é que essa abordagem não distingue contextos diferentes:

  • Uma função chamada exec importada de uma biblioteca interna segura
  • Uma chamada exec com argumento literal fixo, sem entrada externa
  • Uma chamada exec que recebe dados de uma requisição HTTP

Um analisador que compreende a estrutura sintática do código consegue diferenciar melhor esses casos. Em vez de procurar texto, ele identifica elementos estruturais: o tipo da chamada, o nome da função, o tipo dos argumentos.

Mesmo com análise sintática, a ferramenta não tem acesso completo ao contexto de execução. Ela vê a estrutura do código, não o fluxo real dos dados em tempo de execução.

02 Estrutura

O que a ferramenta "vê" ao analisar exec(input)

Considere a instrução abaixo:

exec(input);
Representação estrutural (didática)
Tipo: chamada de função
Função: exec
Argumento [0]: identificador input

Representação simplificada para fins didáticos. A AST real produzida por um parser é mais detalhada.

Uma regra baseada em padrão sintáticoCritério que descreve a estrutura do código que a ferramenta deve reconhecer, como "chamada de função com nome X e argumento do tipo Y". pode dizer: "sinalize toda chamada de função chamada exec que receba qualquer argumento". Isso captura exec(input) e exec("echo lab") pelo mesmo motivo: ambas são chamadas da função exec.

Para separar os dois casos, seria necessário analisar o tipo e a origem do argumento, o que exige análise de fluxo de dadosTécnica que rastreia como um valor se propaga pelo programa, desde sua origem (source) até o ponto onde é utilizado (sink)..

03 Dois casos

Uma regra, duas ocorrências diferentes

A regra exec(...) encontra ambas as chamadas abaixo:

Exemplo A: argumento variável
function run(input: string) {
  exec(input);
}

O argumento é um identificador. A ferramenta não sabe se input vem de uma fonte confiável ou de uma requisição HTTP.

Exemplo B: argumento literal
function staticRun() {
  exec('echo lab');
}

O argumento é uma string literal fixa. Não há entrada externa evidente, mas a regra ainda pode gerar um alerta.

04 O que concluir

O que a ferramenta pode e não pode concluir

Quando a ferramenta gera um alerta, ela está dizendo: "encontrei uma correspondênciaTrecho de código que satisfaz os critérios definidos em uma regra, também chamado de match. Uma correspondência gera um alerta que precisa ser investigado. com a regra configurada".

Isso não significa, automaticamente, que:

  • Há uma vulnerabilidade confirmada
  • O argumento vem de uma fonte não confiável
  • Existe uma rota de exploração por um atacante

A ferramenta gerou uma proposta de investigação. Cabe ao time verificar o contexto: de onde vem o argumento, existe sanitização, o código é atingível por uma entrada externa.

Um alerta é o início da investigação, não a sua conclusão.

Esta é a etapa mais crítica. O alerta diz que a regra foi acionada, mas não diz se o argumento vem de uma fonte confiável ou de uma entrada externa não sanitizada.

Decisão: corrigir, investigar mais ou justificar descarte?

Com base nas etapas anteriores, o time pode tomar uma de três decisões:

  • Corrigir: vulnerabilidade confirmada, corrigir o código e registrar a correção.
  • Investigar mais: contexto inconclusivoSituação em que o contexto disponível não é suficiente para confirmar ou descartar um alerta. Requer mais informação antes de uma decisão., documentar o que falta e quem é responsável.

Qual é a decisão e quem é responsável por ela? A justificativa está registrada de forma rastreável?

Não equipare a contagem bruta de alertas ao número de vulnerabilidades comprovadas. Cada alerta é uma proposta de investigação.

A contagem de alertas não é uma métrica de segurança.

Uma ferramenta que gera 200 alertas e uma que gera 20 não são, necessariamente, mais ou menos seguras. O que importa é quantos alertas foram investigados, classificados e tratados de forma justificada.

Fundamentação teórica · 3

Falsos positivos, falsos negativos e precisão

01

Verdadeiro positivo (VP): alerta corresponde a um problema confirmado segundo critério definido.

Cenário: consulta SQL com entrada externa

Código sinalizado 
const email = req.query.email;

const sql = `
  SELECT * FROM users
  WHERE email = '${email}'
`;

await prisma.$queryRawUnsafe(sql);
O que a ferramenta encontrou

Uma consulta SQL construída por interpolação de um valor recebido da requisição HTTP.

O que o analista investigou

Verificou se o conteúdo de email é controlável externamente e se existe parametrização adequada antes da execução.

Conclusão

Verdadeiro positivo. A entrada não confiável pode alterar a estrutura da consulta SQL. O alerta corresponde a um problema real.

O verdadeiro positivo exige correspondência entre o alerta e uma condição de vulnerabilidade demonstrada.
02

Falso positivo (FP): alerta sinaliza como vulnerabilidade um caso não vulnerável no contexto validado. Marcar FP apenas para "limpar painel" sem justificativa é uma prática problemática.

Cenário: execução de comando constante

Código sinalizado 
import { exec } from "node:child_process";

exec("date", (error, stdout) => {
  if (error) {
    return;
  }

  console.log(stdout);
});
O que a ferramenta encontrou

Uma regra para detectar possíveis injeções de comandos sinalizou uma chamada a exec.

O que o analista investigou

O argumento é uma string constante e não depende de informações fornecidas pelo usuário.

Conclusão

Falso positivo para a hipótese de injeção investigada. A chamada corresponde ao padrão, mas não demonstra injeção por entrada externa no contexto apresentado.

A presença de uma função potencialmente perigosa não comprova, isoladamente, uma vulnerabilidade.
O descarte é específico ao alerta e à hipótese analisada. Não significa que toda utilização de exec seja segura.
03

Falso negativo (FN): uma vulnerabilidade presente no código não é sinalizada pela regra. Só pode ser contado se houver referência independente.

Cenário: desconto acima do limite autorizado

Situação

Fundamentação teórica · 4

Semgrep: como ensinar uma ferramenta a encontrar padrões no código?

Até aqui, vimos que uma análise estática consegue identificar estruturas suspeitas no código, mas que seus alertas precisam ser interpretados.

Agora vamos conhecer a ferramenta que utilizaremos no laboratório: Semgrep. Ela permite analisar código-fonte utilizando regras que descrevem padrões ou condições que desejamos identificar. Além de executar regras existentes, podemos criar nossas próprias verificações.

Mas como transformamos uma preocupação de segurança em uma regra que a ferramenta consiga executar?

01

Primeiro, precisamos definir o que procurar

Imagine que estamos revisando uma API Node.js e queremos identificar chamadas à função exec, que pode executar comandos do sistema operacional.

Nossa hipótese de investigação:

"Quero localizar chamadas à função exec para verificar se os argumentos utilizados podem representar um risco de injeção de comandos."

Observe que ainda não estamos afirmando que todas as chamadas são vulneráveis. Queremos apenas identificar ocorrências para analisá-las.

Objetivo Encontrar chamadas à função exec. Padrão exec($COMMAND) Resultado esperado A ferramenta identifica chamadas que correspondem a essa estrutura. A metavariávelRepresentação de uma parte variável do código. $COMMAND captura qualquer expressão utilizada como argumento, sem exigir conhecimento antecipado do valor exato. $COMMAND representa a expressão utilizada como argumento.
02

Como essa regra é escrita?

As regras do Semgrep podem ser declaradas em arquivos YAMLFormato de representação de dados frequentemente utilizado em arquivos de configuração. Legível por humanos e amplamente adotado por ferramentas de desenvolvimento.. Selecione um campo no código abaixo para ver o que ele representa.

rules:
  - id: review-exec-usage
    languages:
      - typescript
    severity: MEDIUM
    message: >-
      Revise a origem do argumento $COMMAND
      utilizado na chamada a exec().
    pattern: exec($COMMAND)
    metadata:
      category: security
      cwe: "CWE-78Common Weakness Enumeration 78: neutralização inadequada de elementos especiais em comandos de sistema operacional."

Selecione um campo no código YAML para ver sua explicação.

Para lembrar

Uma regra Semgrep transforma uma hipótese de investigação em um padrão que pode ser procurado automaticamente no código.

03

O que essa regra realmente identifica?

Vamos analisar duas implementações diferentes e ver o que a regra encontra em cada uma.

Exemplo A Argumento recebido por parâmetro 
import { exec } from "node:child_process";

function runCommand(command: string) {
  exec(command);
}
Correspondência encontrada

A regra identifica exec(command). Mas o resultado não comprova que existe uma vulnerabilidade.

Precisamos investigar de onde vem command. Se o valor puder ser controlado externamente sem proteção adequada, pode existir risco.

Resultado: correspondência encontrada. Investigação necessária.

Exemplo B Argumento constante 
import { exec } from "node:child_process";

function showDate() {
  exec("date");
}
Correspondência encontrada

A mesma regra também pode encontrar exec("date"). Mas o argumento é uma string fixa.

Nesse trecho, não existe evidência de que uma entrada externa está sendo utilizada para construir o comando.

Resultado: correspondência encontrada, mas sem demonstração de injeção por entrada externa.

O que aprendemos?

A regra reconhece a estrutura exec(...), mas não foi construída para verificar a origem dos argumentos.

Por isso, duas chamadas com características diferentes podem produzir o mesmo alerta. Essa é uma das razões pelas quais a análise automatizada exige triagem.

04

Como podemos melhorar nossa regra?

Podemos combinar um padrão positivo com uma exclusão usando pattern-notCondição utilizada para excluir correspondências que atendem a um padrão específico. Deve ser usada em conjunto com patterns. para deixar de sinalizar chamadas cujo argumento é um literal de string.

rules:
  - id: review-exec-usage
    languages: [typescript]
    severity: MEDIUM
    message: >-
      Revise a origem do argumento $COMMAND
    pattern: exec($COMMAND)
    metadata:
      cwe: "CWE-78"
rules:
  - id: review-exec-nonliteral
    languages: [typescript]
    severity: MEDIUM
    message: >-
      Chamada a exec() com argumento que exige investigação
    patterns:
      - pattern: exec($COMMAND)
      - pattern-not: exec("...")
    metadata:
      cwe: "CWE-78"

patternsPermite combinar condições que devem ser satisfeitas em conjunto para que a correspondência ocorra. combina condições. pattern-not: exec("...") exclui chamadas com argumento literal. O ...Dentro de aspas ("..."), corresponde ao conteúdo de um literal de string. Seu comportamento depende do contexto sintático. dentro das aspas corresponde ao conteúdo de um literal.

Refinar uma regra pode reduzir falsos positivos, mas também pode deixar de detectar situações importantes. Toda alteração precisa ser testada.

05

E quando o problema depende do caminho percorrido pelos dados?

Até agora, nossas regras procuraram estruturas específicas do código. Mas determinadas vulnerabilidades dependem do caminho percorrido pelos dados: um valor recebido de uma requisição HTTP, encaminhado entre funções, chega a uma operação sensível sem proteção adequada.

Para investigar esse tipo de situação, o Semgrep oferece um modo de análise de contaminaçãoTaint analysis: rastreia a propagação de dados considerados não confiáveis desde sua origem até operações sensíveis., conhecido como taint analysis.

Importante: a capacidade de acompanhar os dados depende do mecanismo utilizado, da linguagem e dos limites da análise. Uma regra de padrão simples não equivale automaticamente a uma análise completa de fluxo de dados.
06

Como transformar nossa regra em uma análise de fluxo de dados?

Na seção anterior, construímos uma regra que identifica chamadas à função exec(). Entretanto, ela não consegue determinar, apenas pela correspondência sintática, se o argumento utilizado veio de uma requisição HTTP.

Vamos acrescentar uma nova capacidade à nossa investigação: acompanhar a origem do dado até a operação sensível.

1

Nossa regra anterior: reconhecimento de padrão

rules:
  - id: review-exec-usage
    languages: [typescript]
    severity: MEDIUM
    message: Revise o argumento utilizado em exec()
    pattern: exec($COMMAND)

Essa regra procura chamadas a exec, independentemente da origem do argumento. Por isso, pode sinalizar tanto exec(command) quanto exec("date").

2

Nova regra: análise de contaminação

Agora vamos configurar onde os dados entram e qual operação queremos monitorar.

rules:
  - id: http-input-to-exec
    languages: [typescript]
    severity: HIGH
    mode: taint

    message: >-
      Dados de uma requisição HTTP podem
      alcançar uma execução de comando.

    pattern-sources:
      - pattern: req.query.command
        exact: true

    pattern-sinks:
      - patterns:
          - pattern: exec($COMMAND)
          - focus-metavariable: $COMMAND

    metadata:
      cwe: "CWE-78"

O que mudou?

  • mode: taint: Ativa o acompanhamento de dados considerados não confiáveis.
  • pattern-sources: Define req.query.command como uma origem de dados que precisam ser investigados.
  • pattern-sinks: Define a chamada a exec como uma operação sensível.
  • focus-metavariable: Indica que o argumento $COMMAND é a parte relevante para verificar a chegada de dados contaminados.

Diferentemente da regra anterior, essa configuração busca uma relação entre a origem do dado e seu uso na operação sensível.

3

Vamos observar o comportamento esperado

Exemplo A Dado externo chega diretamente ao comando

exec(command);

Resultado esperado: A regra sinaliza o fluxo. O valor recebido da requisição é encaminhado diretamente para a operação sensível.

Exemplo B Comando constante 
exec("date");

Resultado esperado: A regra não sinaliza esse trecho. Embora exista uma chamada a exec, não há fluxo da origem definida pela regra até o argumento.

Regra de padrão

07

Como executar uma regra personalizada?

Depois de criar o arquivo YAML, podemos utilizar a interface de linha de comando do Semgrep. Considere que a regra foi salva em rules/review-exec.yaml.

semgrep scan --config rules/review-exec.yaml src/

O resultado pode apresentar:

  • Identificador da regra acionada
  • Arquivo e localização da ocorrência
  • Trecho de código correspondente
  • Mensagem configurada
  • Severidade atribuída pela regra

O próximo passo é investigar os resultados e registrar as conclusões. Não basta copiar a saída do terminal: precisamos explicar o que a ferramenta encontrou e por que determinada ocorrência representa, ou não, um problema de segurança.

Conclusão

Criar uma regra Semgrep é definir o que procurar, executar a análise, interpretar os resultados e ajustar a detecção com base nas evidências. A ferramenta automatiza parte da investigação. O analista continua responsável por avaliar o contexto e justificar as conclusões.

Como investigar um alerta antes de classificá-lo?

Cenário em investigação

O Semgrep sinalizou exec(command) como potencial injeção de comandos. Mas o alerta, sozinho, não confirma nada. Ele aponta uma estrutura: a ferramenta reconheceu o padrão. O que fazemos a seguir?

Cada etapa abaixo representa uma pergunta que deve ser respondida antes de qualquer julgamento sobre o alerta.

01

Identificar: o que a ferramenta encontrou?

O primeiro passo é ler o alerta com precisão. Precisamos saber qual regra foi executada, em qual arquivo e função a ocorrência aparece e qual é a linha exata.

  • Qual regra produziu o alerta?
  • Em qual arquivo, função e linha?
  • O que exatamente foi reconhecido pelo padrão?
Pergunta orientadora: Se precisasse descrever o alerta para um colega em uma frase, o que diria?

Alerta identificado: regra review-exec-usage, arquivo server.ts, função runMaintenance, linha 7. O padrão detectado é a chamada exec(command). O argumento command é uma variável, não um literal fixo.

Com essa descrição, já é possível comunicar o alerta. Mas ainda não sabemos se existe um risco real.

02

Rastrear: de onde vem o dado?

Depois de identificar o alerta, precisamos seguir o dado. A fonte do dadoPonto de entrada de um dado no sistema: pode ser uma requisição HTTP, um arquivo, uma variável de ambiente, uma consulta ao banco de dados, entre outros. é o ponto de partida: de onde veio o valor que chega à operação sinalizada?

  • O argumento é um literal fixo, uma variável local ou dado externo?
  • Se é uma variável, quem define seu valor?
  • O valor vem de uma requisição, arquivo ou banco de dados?
Pergunta orientadora: Se um atacante controlasse a entrada do sistema, conseguiria influenciar esse argumento?

Rastreamento no cenário: o parâmetro command chega a runMaintenance como argumento. Ao verificar quem chama essa função, encontramos uma rota HTTP que extrai o valor de req.body.command. A fonte é uma requisição HTTP controlada pelo cliente.

Isso é relevante: o dado não é fixo nem gerado internamente. Vem de fora do sistema.

03

Validar: o caminho é alcançável e há controles?

Com a fonte identificada, verificamos duas coisas: se o caminho é alcançávelAlcançabilidade indica se existe um caminho de execução real que leva ao trecho analisado, considerando rotas, chamadas de função e condições existentes no código. em produção e se existe algum controle sobre o dado antes de chegar à operação sinalizada.

  • A rota ou função é acessível em produção?
  • Existe validação, lista de permissões ou sanitização no caminho?
  • O controle é suficiente para impedir uso malicioso?
Pergunta orientadora: Um atacante externo conseguiria acionar esse caminho sem obstáculo para o valor que envia?

Validação no cenário: a rota POST /maintenance/run é acessível para usuários autenticados. Não há uma lista de comandos permitidos nem filtragem do valor de req.body.command antes de ele ser passado a runMaintenance. O caminho é alcançável e o dado não tem controle identificado.

A ausência de controle visível no fluxo sustenta o risco.

Com as evidências coletadas, é hora de decidir. A classificação deve refletir o que as evidências sustentam. Verdadeiro positivo

Evidências sustentam o risco. Registrar e recomendar correção.

Falso positivo

Padrão detectado, mas evidências descartam o risco. Registrar justificativa.

Necessita investigação

Evidências insuficientes. Registrar o que falta e quem deve investigar.

Risco aceito

Risco conhecido e gerenciado. Registrar a decisão e a justificativa.

Pergunta orientadora: O que as evidências mostram? Sua classificação pode ser justificada pelo que foi coletado?

Decisão no cenário: fonte HTTP confirmada, caminho alcançável, sem controle identificado no fluxo. Classificação: verdadeiro positivo para o cenário didático apresentado. Triagem do alerta exec(command)

Etapa 1 de 2 - O primeiro sinal

O SAST retornou o alerta abaixo para a função runMaintenance. Leia as informações disponíveis antes de responder.

// server.ts - função analisada
function runMaintenance(command: string): void {
  exec(command);       // <-- alerta: review-exec-usage
}
Alerta identificado pelo SAST
Regrareview-exec-usage
Operação sinalizadaexec(command)
Risco investigadoPossível injeção de comandos
Origem de commandAinda desconhecida

Com as informações acima, qual é a classificação mais adequada para este alerta?

Ainda não é possível confirmar. O alerta indica que o padrão foi encontrado, mas não informa se o dado vem de uma entrada externa. Para classificar como verdadeiro positivo, precisamos rastrear a origem de command.
Esta decisão é prematura. Para descartar como falso positivo, precisamos de evidências que mostrem que o dado não é controlado externamente. Sem rastrear a origem, não temos como justificar o descarte.
Decisão fundamentada. Com as informações disponíveis, não é possível confirmar nem descartar. A origem de command é desconhecida. A próxima etapa é rastrear de onde esse valor vem.

Uma nova evidência foi encontrada. O código que chama runMaintenance foi localizado.

Etapa 2 de 2 - Uma nova evidência

O código abaixo foi encontrado na mesma base. Leia o fluxo completo antes de decidir.

// routes/maintenance.ts
router.post('/maintenance/run', authenticate, (req, res) => {
  const command = req.body.command;   // entrada do cliente HTTP
  runMaintenance(command);
  res.json({ status: 'done' });
});
Entrada HTTP req.body.command
→
Função intermediária runMaintenance(command)
→
Operação sensível exec(command)

Com o fluxo completo, qual é a classificação correta para este cenário didático?

Classificação correta para este cenário. O fluxo HTTP → runMaintenance → exec é demonstrado. A autenticação controla quem acessa, mas não filtra o valor de command. As evidências sustentam um verdadeiro positivo.
Atenção com essa lógica. Autenticação define quem pode acessar uma rota, não filtra os valores passados por ela. Um usuário autenticado ainda pode enviar um comando arbitrário se não houver filtragem do conteúdo.
Observação válida, mas incompleta. Mesmo sem saber os detalhes de authenticate, o fluxo já mostra que req.body.command chega a exec sem filtragem visível. Podemos registrar isso como ponto de atenção, mas as evidências atuais já justificam a classificação.

O que mudou entre as duas etapas?

Etapa 1: só tínhamos o alerta. A origem de command era desconhecida. A decisão correta era necessita investigação.

Etapa 2: rastreamos a origem até req.body.command. O fluxo completo foi demonstrado. Com as evidências coletadas, a classificação para este cenário didático é verdadeiro positivo.

Conclusão: a mesma ocorrência de exec(command) pode ter classificações diferentes dependendo do que a investigação revela. O alerta foi o ponto de partida, não a resposta.

Dois modos de documentar o mesmo alerta

Classificar um alerta é só parte do trabalho. O resultado precisa ser documentado de forma que qualquer pessoa da equipe consiga reproduzir a análise e entender a decisão. Compare os dois registros abaixo para o mesmo alerta exec(command).

Exemplo de registro insuficiente
"O Semgrep encontrou um problema de segurança na função exec. É necessário corrigir."

O que está faltando nesse registro:

  • Qual regra produziu o alerta
  • Localização exata no código (arquivo, função, linha)
  • Origem e propagação do dado
  • Evidência que sustenta a conclusão
  • Impacto potencial se explorado
  • Recomendação técnica específica
  • Versão do Semgrep e commit analisado (reprodutibilidade)
ACH-SAST-001
Entrada HTTP encaminhada a execução de comandos

Classificação e regra

Classificação: Verdadeiro positivo (cenário didático apresentado).

Regra: review-exec-usage  |  Localização: server.ts, função runMaintenance, linha 7.

Descrição e fluxo

O sistema recebe um valor via req.body.command e o repassa, sem filtro visível, até a chamada exec(command). Fluxo demonstrado:

req.body.command → runMaintenance(command) → exec(command)

Evidência

O código demonstra um caminho de req.body.command até exec sem restrição de valor identificada. A autenticação controla o acesso à rota, mas não filtra o conteúdo de command.

Impacto potencial

Execução de comandos arbitrários com os privilégios do processo, em qualquer sistema operacional que o servidor execute.

Recomendação

Substituir a execução de comandos arbitrários por operações predefinidas e autorizadas. Se a execução de processos externos for necessária, usar execFile com o executável fixo e argumentos validados por lista de permissões.

Confiança e reprodutibilidade

Nível de confiança: alto para o cenário apresentado.

Para reproduzir: registrar versão do Semgrep, conjunto de regras, commit e localização exata no relatório final.

Etapa 3: nossa primeira auditoria automatizada

Na aula anterior, investigamos manualmente o código da API. Agora utilizaremos o Semgrep para automatizar parte dessa investigação. O objetivo não é encontrar o maior número de alertas, mas compreender o que a ferramenta detectou, investigar os resultados e criar uma regra própria.

Percurso de trabalho

01

Preservar a revisão manual

Finalize e faça commit dos achados manuais antes da primeira varredura automatizada.

02

Executar o Semgrep

Use o Docker com as regras de rules/classroom.yml. Registre versão e commit.

03

Investigar os alertas

Examine cada resultado, identifique regra, contexto e evidências antes de classificar.

04

Criar uma regra personalizada

Desenvolva um YAML simples, com um caso que gera alerta e outro que não deve gerar.

05

Registrar e comparar

Documente a execução e compare com os achados da revisão manual anterior.

O que deverá ficar registrado?

  • entregas/03_semgrep.md Relatório com os comandos utilizados, versão e configuração da ferramenta, alertas investigados, evidências, justificativas e comparação com a revisão manual.
  • rules/minha-regra.yml Regra personalizada desenvolvida pela equipe, com exemplos de correspondência esperada e não correspondência.

Entrega parcial formal
